# 현장 운영·도입·검증 기획안

작성일: 2026-09-16 · 2차 검토일: 2026-09-17. 대화와 제품·화면·기술 기획을 바탕으로 검토한 운영 제안이다.
실제 교회 기기, 네트워크, 운영 인원은 아직 조사하지 않았으며 아래 검증은 수행할 계획이다.
사용자 확정 요구인 개인 스마트폰↔Mac 브라우저, 개인별 사전 요청 버튼, 보조 입력, 간단 로그인을 유지한다.
버튼 설정의 상세 화면과 편집 규칙은 후속 기획으로 남긴다. 음성·영상이나 장비 자동 제어는 이번 운영 대상이 아니다.
2차 검토에서는 담당자 이탈, 계정 복구·교체, 결과 불명인 작업, 정전·업데이트·과거 백업 복원과 기록 삭제의 경계를 보완한다.

## 1. 누가 운영하는가

첫 도입은 한 교회의 한 예배 회차를 대상으로 제안한다. 동시 참여자 수는 실제 봉사자 명단으로 정한다.
이름만 등록된 계정과 오늘 예배에서 맡은 업무를 구분하고, 예배마다 실제 담당자를 확인한다.

| 담당 | 책임 |
|---|---|
| 현장 운영 책임자 | 사용 여부 결정, 당일 수신 담당자 지정, 장애 시 대체 소통 안내; 별도 권한이 있으면 접수 개시·종료 |
| 방송실 재배정 책임자 | 해당 회차의 방송실 역할·재배정 권한으로 담당 이탈 시 실제 조정 확인, 사유·새 담당자 기록 |
| 방송실 수신 담당자 | 요청 목록 확인, 직접 확인 응답, 처리 담당자와 조율, 교대 인계 |
| 인도자 | 본인 계정·예배·버튼 점검, 필요한 요청 전송, 필요할 때 결과 확인 |
| 계정 관리자 | 본인 확인 후 계정 발급·복구·회수, 역할 관리 |
| 서비스 운영자 | 배포, 서버·백업 점검, 장애 복구, 보관 정책 실행 |

한 사람이 관리·운영 책임을 함께 맡을 수 있다. 다만 첫 버전은 한 회차에 인도자 또는 방송실 중 하나의 운영 역할을 부여하는 제안이며, 계정 관리 권한은 별개다.
별도 직책이나 추가 봉사자 채용을 전제로 하지 않는다. 주 담당자 부재 때 연락할 대체 담당자를 정하되 관리자 공용 계정을 나누어 쓰지 않는다.
방송실 연결 표시와 접속자 수는 통신 정보다. 사람이 요청을 보고 있거나 즉시 대응한다는 보장이 아니다.
당일 수신 담당자가 다른 일을 오래 맡으면 대체 담당자를 정한다. 자동 담당 배정 기능은 초기 필수로 만들지 않는다.

## 2. 계정 발급·교대·회수

- 관리자 발급 방식은 권장안이다. 봉사자 명단과 대면 확인 등 교회의 기존 확인 경로로 사용자를 확인한다.
- 아이디·비밀번호를 채택하면 개인별 계정을 발급하고 초기 비밀번호 변경·분실 복구를 예배 전에 마친다.
- 표시 이름만 보고 다른 사람의 비밀번호를 재설정하지 않으며, 비밀번호를 공동 명단에 적어 두지 않는다.
- 개인 스마트폰은 로그인 유지를 선택할 수 있게 한다. 분실자는 다른 연락 경로로 계정 관리자에게 알리고, 관리자는 기기 세션·새 알림 발송을 회수한다.
- 분실 기기를 확실히 구분할 수 없으면 관리자는 본인 확인 후 해당 사용자의 전체 세션을 폐기하고 안전한 기기에서 다시 로그인하게 한다. 이미 본 화면·전달된 알림까지 지워진다고 안내하지 않는다.
- 관리자 부재 때는 미리 지정한 개인 계정의 대체 관리자가 처리한다. 둘 다 대응할 수 없으면 현장 책임자는 대체 연락으로 운영하고, 권한 없는 사람에게 복구·재배정을 맡기지 않는다.
- 비밀번호 분실·초대 만료는 본인 확인 후 기존 계정으로 복구한다. 임시 중복 계정이나 타인 계정으로 우회하지 않으며, 복구 후 개인 버튼·회차 권한을 각각 확인한다.
- 공용 Mac은 이전 담당자의 계정을 빌려 쓰지 않는다. 교대자는 본인 계정으로 같은 예배에 참여한다.
- 교대 전에 미확인 요청, 진행 중인 조정, 아직 답하지 못한 인도자를 함께 확인한다.
- 이전 담당자의 로그아웃과 다음 담당자의 접속 사이에는 합의된 대체 연락을 사용하거나 인계 시간을 짧게 겹친다.
- 맡은 요청을 인계할 때 담당 변경을 기록한다. 조정 중인 장비를 누가 실제로 맡았는지도 구두로 확인한다.
- 담당자가 복귀할 수 없으면 회차의 방송실 재배정 책임자가 실제 조정 여부를 먼저 확인하고 사유·새 담당자를 기록한다. 재배정 권한자도 없으면 대체 연락으로 처리하고 시스템 완료를 추정하지 않는다.
- 정상 역할 변경은 맡은 요청 인계 후 적용한다. 분실·긴급 권한 회수는 인계를 기다리지 않고 접근부터 막은 뒤 책임자가 남은 요청을 재배정한다.
- 역할 변경·봉사 중단 시 권한과 필요한 세션·알림 구독을 회수하고 다른 회차 권한도 점검한다. 일시 통신 단절만으로 담당을 자동 해제하지 않는다.
- 계정 비활성화와 과거 기록 삭제는 별개로 다룬다. 보관 정책에 맞춰 이력의 표시 이름 처리까지 정한다.

공용 Mac 계정 교체 시 이전 본문·초안·화면을 지우고, 접수 결과가 불명인 작업의 최소 식별자만 원 계정별로 격리한다.
다른 계정에서는 그 식별자를 표시·조회·재시도하지 않는다. 원 계정으로 재로그인하면 서버 결과부터 조회하며 이전 명령을 자동 실행하지 않는다.
로그아웃과 로컬 내용 삭제는 서버 전송 취소가 아니다. 오프라인 로그아웃은 화면을 잠글 뿐 서버 세션 회수 완료가 아님을 알리고, 같은 브라우저 계정 교체는 서버 폐기를 확인한 후 진행한다.
설치·재설치·브라우저 데이터 삭제 뒤 로그인·알림·로컬 작업 식별자가 그대로 이어진다고 가정하지 않는다. 다시 인증한 뒤 서버 이력과 개인 버튼을 확인한다.

## 3. 연습과 실제 예배를 구분하는 방법

연습용 예배 회차에는 화면 전체에서 알아볼 수 있는 ‘연습’ 표시를 두고 실제 예배와 다른 회차 ID를 사용한다.
연습 요청·응답·푸시는 연습 참여자에게만 전달하며, 실제 예배 미확인 목록이나 운영 지표에 합치지 않는다.
장애 재현은 연습 회차와 시험 환경에서 진행한다. 실제 예배 중 서버 중단이나 네트워크 차단 실험은 하지 않는다.
당일 접속 점검도 연습 회차에서 수행한 뒤 실제 회차의 날짜·시간·참여 역할을 다시 확인한다.
실제 요청을 시작하기 전에 방송실과 인도자가 같은 회차인지 확인하며, 연습의 미전송 요청을 가져오지 않는다.

| 실제 회차 상태 | 현장에서 할 일 |
|---|---|
| 준비 | 권한자가 참여자를 허용하고 이름·역할·버튼을 확인; 실제 요청은 아직 보내지 않음 |
| 진행·접수 중 | 권한자가 수신 준비를 확인해 접수를 엶; 예배 시작 전 실제 모니터 조정부터 사용 가능 |
| 종료 | 권한·보관 기간 안에서 조회만 허용; 새 요청·답변·피드백·상태 변경 금지, 첫 버전 재개 보류 |

회차 선택 화면이 비었으면 준비 담당자가 회차 존재·참여 권한부터 확인한다. 목록 조회 장애를 ‘오늘 예배 없음’으로 처리하지 않는다.
전날 회차가 닫히지 않았으면 책임자가 미처리 상태와 실제 조정을 확인해 마감한 뒤 오늘 회차를 연다. 시간 경과만으로 완료하지 않는다.

## 4. 예배 전에 준비할 일

1. 운영 책임자가 오늘 예배와 수신 담당자를 정하고, 장애 때 사용할 대체 연락 방법을 참여자에게 공유한다.
2. 방송실은 Mac의 실제 OS·브라우저 버전, 전원, 잠자기 설정, 통신 상태를 확인한다.
3. Mac이 자막·영상·녹음·송출도 맡는지 확인하고, 수신함과 OS 알림이 성도 화면에 나가지 않는 배치를 정한다.
4. 알림 소리를 사용할 경우 예배 스피커·녹화·송출 오디오에 들어가지 않는지 실제 출력 경로로 시험한다.
5. 인도자는 개인 스마트폰의 본인 이름, 배터리, 현재 예배, 저장한 요청 버튼을 확인한다.
6. 모니터 요청이 누구의 어떤 모니터를 뜻하는지 인도자와 방송실이 합의한다. 장비 자산관리 기능까지 요구하지 않는다.
7. 설치·알림을 사용하는 기기는 잠금 후 시험 응답을 확인하고, 알림을 쓰지 않는 사람은 화면 재확인 방법을 익힌다.
8. 통신과 사람의 확인을 함께 시험한 뒤 실제 예배에 참여하고 권한자가 접수를 연다. 연결 성공만으로 준비 완료를 판단하지 않는다.

개인별 버튼은 회차가 바뀌어도 유지되어야 한다. 연습용 기본 버튼만 있는 상태를 설정 기능 완성으로 보지 않는다.
서비스 운영자는 새 배포와 인증·네트워크 설정 변경을 예배 직전에 하지 않고, 변경 후 연습 회차에서 요청·응답을 확인한다.
Mac·휴대폰·브라우저·PWA 업데이트 뒤에는 설치·로그인·권한·알림을 다시 점검한다. 예배 중 강제 새로고침·예전 명령 재생을 유발하는 업데이트는 적용하지 않는다.

## 5. 예배 중과 예배 후 운영

방송실 수신 담당자는 새 요청의 사람·내용·시간을 확인한 뒤 ‘확인했어요’를 누르고 실제 조정을 맡는다.
행동 요청은 확인 뒤 조정 결과까지 기록하고, 단순 안내는 수신자가 명시적으로 확인해 ‘확인 완료(안내)’로 끝낸다. 기존 요청의 답변에는 별도 완료 동작을 요구하지 않는다.
처리할 수 없으면 이유를 짧게 응답한다. 화면에 오래 남았다는 이유로 완료 처리하거나 자동 삭제하지 않는다.
여러 담당자가 있어도 이미 맡은 요청의 담당자를 확인하고, 같은 장비를 동시에 조정하지 않도록 협의한다.
인도자가 ‘이제 괜찮아요’를 누르지 않아도 완료 응답을 취소하지 않는다. 추가 조정은 원 요청에 연결된 새 요청을 권장한다.
‘처리할 수 없어요’는 사유를 남기고 처리 불가로 종료하는 응답이다. 잠시 지연되는 경우에는 답변으로 알리고 처리 중 상태를 유지한다.
전달된 지 오래된 요청은 찬양·설교 등 진행 상황을 확인한 뒤 조정한다. 과거 요청을 현재 필요로 추정하지 않는다.
취소가 먼저 서버에 확정됐어도 이미 조정했다면 취소 상태를 유지하고 진행 회차의 답변에 실제 조정 사실을 남긴다. 이후 추가 조정은 원 요청에 연결된 새 요청이다.

예배 후에는 권한 있는 사람이 미해결 요청을 검토하고 회차를 종료한다.
완료하지 못한 요청은 ‘종료로 마감’으로 남기고, 다음 회차로 자동 이월하거나 일괄 완료하지 않는다.
종료와 답변·취소·완료가 겹치면 서버의 먼저 확정된 순서를 확인한다. 종료 뒤 발견한 실제 조정 사실은 접근이 제한된 기존 현장 기록에 요청 ID·사실·작성자를 남기며 회차를 다시 열지 않는다.
개인 버튼은 유지하고 공용 Mac은 로그아웃한다. 다음 담당자가 이전 계정의 알림을 받지 않는지 점검한다.
운영 책임자는 누락·중복·오발송·응답을 못 본 사례를 짧게 기록하고 다음 연습에서 재현할 항목을 고른다.

## 6. 문제가 생겼을 때의 행동

아래 대체 연락은 서비스 도입 전에 교회가 정한다. 예를 들어 지정된 보조 봉사자에게 전달하거나 합의된 최소 신호를 사용한다.
대체 경로로 처리한 요청은 서비스가 복구된 뒤 다시 조정하지 않도록 담당자가 현재 상태를 확인한다.

| 상황 | 인도자·방송실의 행동 | 서비스에서 필요한 표시 |
|---|---|---|
| 수신 담당자 부재·권한 회수 | 책임 권한자가 실제 조정 확인 후 사유를 남겨 재배정; 없으면 대체 연락 | 미확인·처리 중과 인계 필요를 구분 |

무응답 때 대체 연락으로 전환할 기준과 담당자는 예배 전에 정한다. 방송실이 인도자에게 보낸 요청도 방송실 발신 담당자가 확인하며, 푸시 재발송 횟수로 실제 전달을 대신하지 않는다.
작업 ID는 전송·확인·완료·취소·답변 같은 한 번의 변경 시도에 붙이는 식별자다. 결과 불명일 때는 같은 ID로 조회하고 새 ID를 만들어 다시 누르지 않는다.
조회에 아직 없더라도 지연된 원본이 도착할 수 있다. 여전히 필요한 경우 같은 작업 ID·내용으로 수동 재시도하며, 변경 명령은 자동 재전송하지 않는다.
보내려던 작업을 버리려면 서버의 원 시도 폐기 확정을 확인한다. 원본이 먼저 접수됐다면 기존 결과를 확인하고 필요한 요청 취소를 별도로 수행한다.
한 번도 송신하지 않은 로컬 초안만 바로 버릴 수 있다. 이미 송신한 결과 불명 작업은 화면 삭제·로그아웃으로 취소됐다고 판단하지 않는다.
작업 ID를 잃었으면 원 계정의 서버 이력과 방송실 수신 목록을 대조한다. 원 시도의 안전한 종결을 확인할 수 없으면 같은 요청을 새 ID로 만들지 않고 대체 연락으로 처리한다.
저장된 기록을 가져오는 복구와 새 전송은 구분한다. 늦게 도착한 이미 접수된 요청도 담당자가 현재 필요성을 다시 확인한다.
인도자가 휴대폰을 넣은 채 방송실의 선행 요청을 즉시 알아야 하는 상황은 알림 거부 상태만으로 충족할 수 없다.
그 사용자가 화면을 확인하는 운영에 동의했는지 확인하고, 그렇지 않으면 별도 알림 경로 검토 전에는 해당 사용 방식을 출시 준비 완료로 보지 않는다.

## 7. 단계별 도입

**기술 확인:** 실제 사용할 iPhone·Android·Mac의 버전과 네트워크 경로를 기록하고 전송·잠금·재접속을 시험한다.
임시 버튼으로 통신을 시험할 수 있으나 이후 개인별 저장·수정·재사용 기능의 검증이 별도로 필요하다.

**모의 예배:** 실제 자리와 조명, 방송실의 다른 작업을 재현하고 인도자가 폰을 넣었다 꺼내며 사용한다.
여러 요청, 서로 반대되는 요청, 담당 교대, 취소, 늦은 응답, 통신 전환을 순서가 정해진 시나리오로 실행한다.
관찰자는 요청이 전달되는 것뿐 아니라 성도의 주의를 끄는 행동과 방송실의 작업 부담도 기록한다.

**제한 도입:** 합의한 한 회차와 참여자부터 사용하고, 수신 담당자와 대체 연락 담당 경로를 명확히 둔다.
실제 예배 중에는 정상 사용만 관찰하고, 발견한 결함은 예배 후 연습 환경에서 재현한다.
출시 조건을 충족하지 못하면 사용자 수를 늘리지 않고 수정·재검증한다. 회차 수만 채워 자동 통과시키지 않는다.

**확대:** 서로 다른 담당자와 실제 지원 기기에서도 결과가 유지되고 운영자가 복구 절차를 수행할 수 있을 때 확대한다.
동시 예배·추가 예배실을 늘리기 전에는 대상 선택과 권한·요청 분리를 다시 검증한다.
각 단계의 회차 수와 일정은 봉사자 일정 및 결함 결과로 정한다. 현재 완료된 일정이나 성능 실적은 없다.

## 9. 실제 운영에 내보낼 조건

- O01~O24를 적용 가능한 지원 기기·통신 경로에서 통과하고 미실행 항목과 지원 제외 환경을 명시한다. 핵심 경계 시험을 지원 제외라는 이유로 생략하지 않는다.
- 요청자·대상·회차 혼동, 잘못된 완료 표시, 재전송 중복, 타인 기록 노출, 송출 화면 노출은 도입을 멈추는 결함으로 삼는다.
- 버튼 설정 상세 기획을 끝내고 개인별 사전 저장·변경·재사용이 동작해야 한다. 공통 버튼만 있는 시제품은 조건을 충족하지 않는다.
- 휴대폰을 넣는 실제 행동으로 수신 결과를 검증한다. 알림이 없어도 가능한 사용과 즉시 알아야 하는 사용을 구분해 지원 범위를 알린다.
- 현장 책임자·수신 담당자·재배정 권한자·서비스 운영자와 계정 대체 담당자가 정해지고 부재 시 복구·회수·교대·대체 연락을 직접 연습한다.
- 보관·삭제·백업 정책과 복구 목표를 정하고 시험 복구 기록을 남긴다. 빈 값인 채 운영을 시작하지 않는다.
- 작업 결과 불명·폐기 경합, 원 계정으로 돌아오는 흐름, 회차 종료·기록 삭제·과거 복원 후 재실행 차단을 검증한다.
- 배포 후 되돌릴 버전과 데이터 호환성을 확인한다. DB 구조 변경은 단순 코드 교체만으로 되돌아간다고 가정하지 않는다.
- 사용자와 현장 책임자가 남은 제약을 알고 제한 도입 범위를 합의한다. 알림 지연을 사람 확인 성공으로 계산하지 않는다.

## 10. 제안 지표와 측정 방법

아래는 측정 설계이며 실측값이나 보장 수치가 아니다. 관찰 기간과 목표값은 첫 모의 예배 전에 합의한다.

| 지표 | 측정 방법 |
|---|---|
| 요청까지의 조작 부담 | 폰에서 서비스 열기부터 버튼 전송까지 단계·걸린 시간 관찰; 잠금 해제와 앱 내부 시간 구분 |
| 기술 전달 시간 | 서버 접수 시각과 수신 화면 표시 관측값 비교; 기기 시계 차이를 보정하거나 같은 관찰 시계 사용 |
| 사람 확인 시간 | 서버 접수부터 담당자가 확인 응답한 서버 시각까지 측정 |
| 처리 결과 시간 | 담당자 확인부터 완료·처리 불가 시각까지 측정; 종류별 구분 |
| 누락·중복·오발송 | 시험 발신 목록과 최종 요청 ID·수신 대상 대조; 건수와 전체 시도 수 함께 기록 |
| 화면 밖 응답 인지 | 잠금 후 실제 사용자가 응답을 알아차렸는지 관찰; 푸시 발송 로그로 대신하지 않음 |
| 현장 부담 | 재타이핑·폰 재확인·손짓 횟수와 방송실 업무 중단 사례를 같은 시험 구간에서 기록 |
| 운영 복구 | 장애 발견부터 대체 연락 전환·서비스 복구까지 기록하고 복구된 데이터 시점도 명시 |

평균만 기록하지 않고 가장 느린 사례와 실패 조건을 함께 남긴다. 소규모 시험 결과를 전체 기기의 보장으로 확대하지 않는다.
사용자별 봉사 실적을 평가하는 지표로 쓰지 않고 UI·통신·운영 개선에 필요한 범위로 사용한다.

## 11. 클라우드와 교회 내부 서버 비교

개인 스마트폰이 교회 Wi-Fi와 이동통신을 오간다면 외부에서도 같은 주소로 접근할 수 있는 배치를 우선 검토한다.
이는 접근 경로를 단순하게 하려는 기획 판단이며 특정 업체 구매 추천이나 비용 견적이 아니다.

| 조건 | 클라우드 서버 | 교회 내부 서버 |
|---|---|---|
| 폰 이동통신 사용 | 공개 HTTPS 서비스에 접근하는 구조 가능 | 내부망 전용이면 접근 불가; 외부 접근·보안 운영 별도 필요 |
| 교회 인터넷 끊김 | 방송실과 폰 모두 대체 회선이 없으면 이용 불가 | 내부 Wi-Fi·전원·이름 해석·인증 경로가 살아 있어야 내부 사용 가능 |
| 장비 운영 | 제공 범위에 따라 서버·DB·백업 관리 분담 | 교회가 전원·저장장치·업데이트·인증서·복구 장비 관리 |
| 비용 요인 | 컴퓨팅, DB, 저장량, 백업, 외부 전송, 운영 지원 | 장비 구입·교체, 전기, 네트워크, 백업 장소, 관리 인력 |

교회 내부에 두더라도 일반 HTTP 주소만으로 PWA 관련 기능이 모두 동작한다고 가정하지 않는다. 보안 컨텍스트와 인증서 구성을 검증한다. [MDN Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)
외부 인터넷이 끊겨도 내부 채팅이 가능한 설계와 푸시 알림이 가능한 조건은 다르다. iOS Web Push는 Apple의 푸시 서비스를 사용한다. [WebKit 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
선택 전에 실제 Wi-Fi 범위, 이동통신 수신, 외부 회선 장애 이력, 운영자가 관리 가능한 시간을 확인한다. 내부 서버와 클라우드 자동 이중화는 첫 버전 필수로 확대하지 않는다.

## 12. 데이터·보관·백업 운영

최소 저장 범위는 계정 식별자·표시 이름·역할, 개인 버튼, 예배 참여, 요청·답변·상태 이력, 작업 적용·폐기 결과, 필요한 인증·알림 연결 정보다.
전화번호·교인 전체 명단·위치·음성·영상은 이 기능의 기본 필수 정보로 수집하지 않는다. 복구 수단을 추가하면 필요한 정보도 별도 결정한다.
운영 로그에는 요청 ID·오류·지연 등 진단에 필요한 정보를 남기고 비밀번호·세션 토큰·알림 구독 주소·메시지 본문을 무조건 복제하지 않는다.
푸시 구독 주소는 다른 곳에 공개하지 않는 정보로 취급한다. [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)

- 실제 도입 전 메시지·상태 이력, 계정·개인 버튼, 작업 중복 방지·폐기 기록, 진단 로그, 백업을 구분해 보관 기간과 삭제 담당자를 결정한다.
- 요청 기록은 예배 후 문제 검토에 필요한 기간만 남기는 방향으로 정하고, 개인 버튼은 반복 사용 목적에 맞춰 별도 정책을 둔다.
- 회차가 진행 중이면 작업 적용·폐기 기록을 먼저 지우지 않는다. 미종료 회차를 점검하며 보관 기간을 맞추기 위해 진행 요청을 자동 완료하지 않는다.
- 종료 뒤 본문·답변·알림 사본과 작업 기록의 삭제 순서를 함께 정한다. 본문 없는 최소 회차 종료·작업 폐기 식별정보는 보관 종료 판정·재실행 방지에 필요한 범위와 기한만 유지하며 무조건 영구 보관하지 않는다.
- 회차 ID를 재사용하지 않고, 삭제된 회차와 보관 종료 작업은 새 실행을 거절한다. 클라이언트가 존재하지 않는 회차 ID를 생성·재사용할 수 없게 하며 기록 없음은 새 ID 재전송 허가가 아니다.
- 열람 권한은 해당 예배 업무에 맞추며 계정 관리 권한만으로 모든 메시지 열람을 허용하지 않는다.
- 자동 삭제 결과를 점검하고 계정 종료·권한 회수 후의 접근도 시험한다. 백업 속 기록이 언제 사라지는지 함께 안내한다.
- 삭제·권한 회수 운영 내역은 기존의 접근 제한된 운영 기록 등으로 복원 대상 DB와 함께 잃지 않도록 보호한다. 새로운 원장 서비스를 만드는 요구는 아니며, 과거 데이터 복원 시 공개 전에 해당 내역을 다시 적용한다.
- DB와 개인 버튼을 백업하고 저장소 접근권한, 사용하는 암호화 키의 보관 위치, 복구 담당자를 각각 기록한다. 한 사람이 여러 책임을 맡을 수 있으나 같은 고장에 함께 사라지는 단일 복사본은 피한다.
- 백업 주기는 허용 가능한 데이터 손실 시간에 맞추고, 복구 소요 시간 목표와 함께 운영자가 실행 가능한 값으로 정한다.
- 시험 환경에 백업을 복구해 계정·개인 버튼·회차·요청 이력이 맞는지 확인한다. 백업 작업 성공 로그만으로 복구 가능을 판단하지 않는다.

**과거 백업을 복원할 때의 권장 절차:** 운영자가 새 접수·변경·자동 알림을 잠그고, 기존 세션·알림 연결을 무효화한 뒤 복원한다.
복원 DB에서 이전 세션·알림 연결이 살아나지 않았는지 다시 확인한다. 삭제·권한 회수 내역을 재적용할 자료가 부족하면 현장 책임자·계정 관리자가 유효한 계정·권한 명단을 다시 확인하기 전까지 조회 공개와 새 알림도 막는다.
권한 명단 재확인이 과거 삭제 여부까지 증명하지는 않는다. 삭제 여부를 확인할 수 없는 복원 본문은 비공개로 유지하고 운영자가 보관 정책에 따라 공개·정리 범위를 결정한다.
복원 시점 뒤의 요청·취소·권한 회수·예배 종료를 잃었을 수 있으므로, 현장 책임자는 마지막 백업 시각과 실제 장비 상태를 대조한다.
첫 버전에서는 복원된 진행 회차를 쓰기 금지 상태로 복구 사유를 남겨 마감하고, 계속 소통해야 하면 권한자가 새 회차 ID로 개시하는 안을 제안한다. 오래된 회차를 다시 여는 방법은 쓰지 않는다.
새 회차에 요청을 자동 복사하지 않는다. 사람은 현재 필요한 요청만 새로 보내며 운영자는 손실 범위·대조 결과·복구 시각을 별도 기록한다.
기존 알림 대기열을 일괄 발송하지 않는다. 이 절차는 작업 ID 기록이 백업에서 사라져도 옛 탭의 명령이 새로 실행되는 것을 막기 위한 서비스 운영안이다. DB가 유지되는 정상 재시작은 권한·유효성을 다시 확인해 미전송 통지를 복구할 수 있다.
백업 방식 자체는 선택한 환경에 맞춰 정한다. PostgreSQL도 여러 백업·복구 방식을 제공하며, 여기서는 특정 방식의 무손실 복구를 보장하지 않는다. [PostgreSQL 백업·복구](https://www.postgresql.org/docs/current/backup.html)

## 13. 2차 검토의 경계와 남은 결정

‘알림을 거부해도 사용 가능’은 화면을 열어 요청·조회할 수 있다는 뜻이다. 주머니 속 폰으로 즉시 응답을 알아차리는 요구까지 충족한 것은 아니다.
통합안의 ‘처리할 수 없어요’는 처리 불가 종료이고, 단순 지연은 답변이다. 안내는 ‘확인 완료(안내)’로 마치며 행동 요청의 조정 완료와 혼용하지 않는다.
취소된 물리 조정 사실은 진행 회차의 답변 또는 종료 후 기존 현장 기록에 남긴다. 정정만을 위한 종료 회차 재개·완료 덮어쓰기는 추가하지 않는다.
로그아웃 때 본문·초안은 정리하되 결과 불명 작업 ID는 원 계정별로 격리한다. 계정 복귀·보관 종료·백업 복원에서의 조회와 재시도 경계를 화면·기술 문서와 동일하게 유지한다.
Mac 알림은 수신 편의뿐 아니라 성도 화면·송출 오디오에 노출되지 않는 조건도 포함해 검증해야 한다.
추가하지 않은 기능은 자동 담당 해제·자동 재촉, 관리자 공용 비상 로그인, 회차 자동 재개, 오프라인 명령 일괄 실행, 장비 자동 제어, 통계 대시보드다. 실제 확인과 담당 책임을 대신하거나 범위를 크게 늘리기 때문이다.
후속 결정은 기기·통신 실태, 부재 시 대체 책임자, 무응답 전환 기준, 로그인·참여 방식, 보관 기간, 손실·복구 목표다. 정한 숫자는 검증 목표로 표시하며 실측 결과와 구분한다.
