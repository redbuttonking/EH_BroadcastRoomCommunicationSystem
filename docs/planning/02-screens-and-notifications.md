# 화면·알림 UX 기획안

작성일: 2026-09-16 · 2차 검토: 2026-09-17. 사용자와의 대화 및 공식 플랫폼 문서를 기준으로 한 제안이며, 구현·실기기 검증은 아직 하지 않았습니다. 2차 검토에서는 빈 화면·실패·계정 교체·담당 인계·알림 이후의 다음 행동을 보완했습니다.

## 기획의 기준

- 확정 요구: 예배인도자는 개인 스마트폰을 잠깐 꺼내 쓰고, 방송실은 Mac 브라우저에서 사용합니다.
- 확정 요구: 미리 준비한 요청 버튼이 주 기능이며 자유 입력은 보조 기능입니다. 누가 보냈는지 알 수 있도록 로그인합니다.
- 확정 방향: 요청 전송, 방송실의 확인·처리 응답, 인도자의 결과 확인을 하나의 흐름으로 만듭니다.
- 제안: 반응형 웹과 홈 화면에 설치하는 웹 앱(PWA)을 먼저 검증합니다. 별도 네이티브 앱 채택은 확정하지 않습니다.
- 제안: 아이디·비밀번호, 로그인 유지, 관리자 계정 발급은 가능한 시작안입니다. 인증 수단은 별도 결정합니다.
- 보류: 버튼 생성·편집·색상·분류·공유·배치 설정의 자세한 규칙은 후속 기획에서 다룹니다.
- 예배 중 화면의 목표는 “누가, 무엇을 요청했고, 지금 어디까지 진행됐는지”를 짧게 확인하는 것입니다.

## 사용자 여정

### 최초 사용: 예배 전에 준비

1. 서비스 주소에서 계정 안내를 확인합니다. 관리자 발급안을 채택하면 받은 초대로 최초 인증 정보를 설정하고 로그인합니다. 계정이 없거나 초대가 만료됐다면 계정 담당자에게 문의하는 경로를 제공합니다.
2. 참여할 예배를 선택합니다. 예배가 여러 개이면 날짜·시간·장소를 구분해 보여줍니다.
3. 표시 이름·역할을 확인하고 인도자 화면에서 본인의 요청 버튼과 받는 대상인 방송실을 봅니다. 버튼이 없으면 준비 안내를 보여줍니다.
4. 별도 연습 회차에서 방송실과 시험 요청·응답을 확인한 뒤 실제 회차로 이동합니다. 연습 요청과 미전송 문구를 실제 회차로 가져오지 않습니다.
5. 휴대폰을 넣은 뒤 응답을 받는 용도를 설명하고, 지원 기기에서는 홈 화면 설치와 알림 허용을 안내합니다.
6. 알림 설정을 건너뛰어도 화면을 열어 요청하고 응답을 확인할 수 있습니다.
7. 방송실 담당자는 자기 이름으로 로그인한 후 해당 예배 수신함을 열고 수신 상태를 확인합니다.

### 재방문: 요청까지의 단계 줄이기

1. 로그인과 해당 예배 참여가 유효하면 역할에 맞는 홈 화면을 바로 엽니다.
2. 이전 예배가 종료됐으면 새 예배를 안내합니다. 과거 예배로 요청을 자동 전송하지 않습니다.
3. 현재 상태를 서버에서 확인하는 동안 “최신 상태 확인 중”을 표시합니다.
4. 로그인 만료 시 같은 계정으로 재로그인하고 권한·회차를 다시 확인한 뒤 원래 보려던 요청 또는 현재 예배로 돌아옵니다. 이전 전송·처리 행동을 자동 실행하지 않습니다.
5. 매 접속마다 설치·알림 권한 창을 반복해서 띄우지 않습니다.

### 예배 중: 전송과 응답

1. 인도자가 휴대폰에서 홈 화면을 열고 현재 예배와 방송실 연결 상태를 확인합니다.
2. “모니터 크게”를 한 번 누르면 즉시 누른 상태를 표시하고 전송을 시작합니다.
3. 서버에 저장된 뒤 “서버 접수”로 바뀝니다. 이는 방송실 담당자가 봤다는 뜻과 다릅니다.
4. 방송실 담당자가 요청 카드의 “확인했어요”를 누르면 확인 담당자와 시간을 기록합니다.
5. 조정을 마치고 “조정했어요”를 누르면 인도자가 앱 안에서 결과를 보고, 허용된 환경에는 푸시를 시도합니다.
6. 인도자는 “이제 괜찮아요” 또는 “아직 불편해요”로 피드백할 수 있습니다.
7. “아직 불편해요”는 기존 요청과 연결된 추가 요청으로 보여주어 담당자가 앞선 내용을 함께 봅니다.

### 방송실이 먼저 보낸 요청 확인

1. 모바일 홈의 “받은 메시지”는 방송실의 새 요청과 기존 요청에 대한 응답을 함께 보여줍니다.
2. 인도자가 보낸 요청이 없어도 방송실의 “마이크를 가까이 해주세요” 같은 새 요청을 받을 수 있습니다.
3. 행동 요청에는 “방송실 요청”, 단순 전달에는 “방송실 안내”, 답변에는 관련 요청 이름을 표시합니다. 받은 메시지에서는 “확인할 요청·안내”와 “새 응답”을 나눕니다.
4. 인도자가 “확인했어요”를 직접 누르면 방송실에 확인 상태가 전달됩니다. 필요한 경우 직접 답변을 덧붙입니다.
5. 안내는 명시적 확인으로 마칩니다. 행동 요청은 확인 후 “했어요” 또는 사유를 포함한 “할 수 없어요”로 응답합니다. 화면의 문구는 역할에 맞추되 저장되는 처리 상태는 같습니다. 상세 열기만으로 확인 처리하지 않습니다.
6. “확인할 요청·안내” 수는 명시적 확인·취소·종료 상태를 기준으로 갱신합니다. “새 응답” 표시는 해당 내용을 화면에서 열면 지울 수 있으나, 상대에게 사람이 읽었다는 증거로 보내지 않습니다.
7. 확인한 행동 요청은 받은 메시지의 “처리할 요청”에 남기고 완료·처리 불가·취소·종료 때 처리 결과로 옮깁니다. 확인한 안내는 “확인 완료”로 표시합니다.

### 시작하지 못하거나 상대가 없는 경우

| 상황 | 표시와 다음 행동 |
|---|---|
| 로그인 실패·비밀번호 분실 | 계정 존재 여부를 드러내지 않는 실패 문구, 다시 입력·계정 복구 안내를 제공합니다. 복구를 마친 뒤 다시 로그인합니다. |
| 계정 비활성화·참여 권한 없음 | 요청 본문을 숨기고 이용할 수 없음을 알립니다. “참여 가능한 예배 보기”·“계정 담당자 문의”로 이동하며 재로그인만 반복시키지 않습니다. |
| 참여 가능한 예배 없음 | 빈 목록과 조회 실패를 구분합니다. “다시 확인”과 예배 담당자 문의를 제공하고 임의 회차를 만들거나 지난 회차에 전송하지 않습니다. |
| 예배가 준비 상태 | 회차·이름·역할을 확인하고 참여·조회할 수 있지만 전송은 닫혀 있음을 표시합니다. 담당자가 요청 접수를 열면 진행 상태로 바뀝니다. 실제 예배 시작 전 조정도 접수를 연 뒤 가능합니다. |
| 저장한 버튼 없음 | “준비된 요청 버튼이 없어요”와 설정 진입·보조 입력을 제공합니다. 예배 전 준비를 안내하며 버튼 편집 세부나 임의 기본값은 확정하지 않습니다. |
| 버튼·요청 목록 불러오기 실패 | 없음으로 표시하지 않고 “불러오지 못했어요”와 재시도를 제공합니다. 지난 캐시로 현재 권한·진행 상태를 대신하지 않습니다. |
| 내 연결은 정상, 방송실 접속 없음 | “요청은 접수할 수 있으나 현재 접속한 담당자가 없어요”를 표시합니다. 전송 후에도 미확인을 유지하고 급히 조정해야 하면 합의한 대체 연락을 안내합니다. |
| 방송실이 선택한 인도자 접속 없음 | 대상·마지막 확인 가능한 접속 정보와 별개로 부재 표시를 합니다. 권한 있는 대상에게 전송할 수 있지만 확인을 보장하지 않습니다. 즉시 전달이 필요하면 대체 연락을 사용합니다. |
| 이미 종료된 회차 | 종료 시각·마감 상태를 보여주고 새 전송·처리를 막습니다. “현재 예배 찾기”로 이동하며 지난 요청을 새 회차로 복사하지 않습니다. |

로그인 성공과 알림 허용, 예배 참여 성공은 각각 따로 표시합니다. 역할은 서버가 허용한 항목만 선택하며 화면에서 선택했다고 권한을 얻지는 않습니다.

## 화면 목록

| 화면 | 주요 내용 | 진입 시점 |
|---|---|---|
| 로그인 | 인증, 로그인 유지 안내, 계정 문의 경로 | 최초·인증 만료 |
| 예배 선택·참여 | 날짜·시간·장소, 현재 참여 정보 | 처음 참여·예배 변경 |
| 인도자 홈 | 큰 요청 버튼, 최근 요청, 방송실 응답 | 인도자 기본 화면 |
| 방송실 수신함 | 미확인·처리 중 요청, 담당자, 시간 | 방송실 기본 화면 |
| 요청 상세 | 원문, 상태 이력, 답변, 취소 등 가능한 행동 | 요청 카드 선택 |
| 받은 메시지 | 방송실의 새 요청과 기존 요청의 응답 | 수신 표시·알림 선택 |
| 직접 입력 | 받는 대상, 내용, 보내기 | 보조 입력 선택 |
| 예배 전 준비 | 테스트, 설치·알림 안내, 연결 확인 | 필요할 때 |
| 계정·설정 진입 | 계정, 알림 상태, 향후 버튼 설정 진입 | 명시적 선택 |

## 모바일 홈 와이어프레임

아래 이름과 예배 시간은 배치를 설명하기 위한 가상 예시입니다.

```text
┌──────────────────────────┐
│ 09/20 주일 2부 11:00  메뉴 │
│ 김인도 · 찬양인도자        │
│ 받는 곳: 방송실            │
│ 내 연결 정상 · 담당자 1명   │
├──────────────────────────┤
│ 자주 쓰는 요청             │
│ ┌──────────┐ ┌──────────┐ │
│ │ 모니터   │ │ 모니터   │ │
│ │ 크게     │ │ 작게     │ │
│ └──────────┘ └──────────┘ │
│ ┌──────────┐ ┌──────────┐ │
│ │ 마이크   │ │ 냉방     │ │
│ │ 날카로움 │ │ 약하게   │ │
│ └──────────┘ └──────────┘ │
│ [다른 요청 보기]           │
├──────────────────────────┤
│ 최근 요청                  │
│ 모니터 크게 · 방송실 확인  │
│ 이담당 · 11:08             │
│ [요청 상세]                │
├──────────────────────────┤
│ [직접 입력] [받은 메시지]  │
│ 확인할 항목 1 · 새 응답 0  │
└──────────────────────────┘
```

- 2열 배치는 초기 후보입니다. 짧은 화면·큰 글자에서는 1열로 바뀌어도 문구를 자르지 않습니다.
- 자주 쓰는 버튼은 첫 화면에서 찾기 쉬운 곳에 고정합니다. 사용 빈도에 따라 예배 중 자동 재배치하지 않습니다.
- 현재 예배, 연결 상태, 요청 전송 결과는 화면을 가리는 팝업 없이 확인할 수 있어야 합니다.
- 인도자의 사전 요청 버튼은 행동 요청으로 정해 두고 한 번 눌러 전송합니다. 매 전송마다 요청·안내 유형을 다시 고르게 하지 않습니다.
- 최근 요청 영역 높이를 제한하고 새 응답이 와도 요청 버튼이 갑자기 밀려나지 않게 합니다.
- 버튼에는 짧은 이름을 표시하고, 요청 상세와 방송실에는 구체적인 전송 문장을 보여줍니다.
- 같은 버튼을 연속으로 누르면 진행 중인 전송을 보여줍니다. 접수 결과가 불명인 동안에는 그 전송을 먼저 확인하며, 새 요청을 만들어 연타를 재현하지 않습니다. 이미 완료된 시도 후 의도한 새 요청까지 막지는 않습니다.
- 오발송은 상세 화면의 취소 동작으로 알립니다. 이미 조정이 끝난 요청은 취소로 되돌릴 수 없으며, 변경이 필요하면 새 요청을 보냅니다.
- 모든 요청에 확인창을 추가하거나 길게 누르기를 강제하지 않습니다. 예배 중 한 번 누르는 흐름을 우선 검증합니다.

## 방송실 Mac 수신함 와이어프레임

```text
┌──────────────────────────────────────────────────────────────┐
│ 09/20 주일 2부 · 방송실       연결됨       이담당 · 계정        │
│ [미확인 2] [처리 중 1] [처리 결과]        [인도자에게 보내기] │
├───────────────────────────┬──────────────────────────────────┤
│ 미확인 요청                │ 선택한 요청                      │
│ 김인도 · 찬양인도자         │ 김인도 · 모니터 크게              │
│ 모니터 크게 · 11:08:12      │ 제 모니터 스피커 소리를 키워주세요│
│ [확인했어요]               │                                  │
│                           │ 접수 11:08:12                    │
│ 박인도 · 예배인도자         │ 확인 이담당 11:08:18             │
│ 냉방 약하게 · 11:08:30      │                                  │
│ [확인했어요]               │ [조정했어요] [처리할 수 없어요]  │
│                           │ [직접 답변]                      │
├───────────────────────────┴──────────────────────────────────┤
│ 새 요청은 목록에 유지됩니다. 마지막 동기화 11:08:35           │
└──────────────────────────────────────────────────────────────┘
```

- 미확인 요청은 오래된 순서가 기본 후보이며, 새 항목 때문에 선택한 카드가 이동하지 않도록 합니다.
- 새 요청은 개수와 배경 강조로 알립니다. 계속 깜박이거나 화면 전체를 덮지 않습니다.
- 다른 담당자가 먼저 확인하면 담당자 이름을 반영합니다. 확인과 처리를 별개의 행동으로 유지하고 새 요청이 도착해도 선택 중인 요청과 키보드 초점을 바꾸지 않습니다.
- 목록 표시나 상세 열기만으로 “확인했어요”를 대신하지 않습니다. 담당자의 명시적 응답이 필요합니다.
- “처리할 수 없어요”는 이유를 남기고 요청을 처리 불가로 종료합니다. 잠시 기다려야 하는 경우는 직접 답변으로 알리고 처리 중 상태를 유지합니다.
- 처리 결과 목록에서도 원문과 이력을 볼 수 있어야 합니다. 조정 완료·처리 불가·취소·예배 종료를 각각 표시하고, 접수하지 못한 항목은 서버의 처리 결과에 넣지 않습니다.
- 방송실 발신은 현재 회차의 인도자 한 명과 요청·안내 종류를 확인한 뒤 전송합니다. 이전 발신 대상이나 기본값 때문에 다른 사람·전체에게 보내지 않도록 합니다.
- 담당 변경 권한이 있으면 요청 상세에서 “담당 변경”을 열어 현재·다음 담당자를 확인합니다. 서버가 변경을 저장하기 전에는 기존 담당자를 유지하고, 다른 변경과 겹치면 최신 담당자를 보여줍니다.
- 현재 담당자가 실제 업무를 이어갈 수 없거나 권한이 회수되면 “인계 필요”를 표시하고 자동 해제하지 않습니다. 잠깐 접속이 끊겼다는 이유만으로 인계를 시작하지 않습니다. 당일 방송실 책임 권한자가 실제 조정 상황을 확인해 사유와 새 담당자를 남기는 경로를 제공합니다.

## 이동·입력·계정 교체 규칙

- 홈→직접 입력은 새 요청 작성, 요청 상세→직접 답변은 기존 요청에 답변입니다. 제목·받는 대상·원 요청을 표시해 두 동작을 구분하고 서버 접수 후에만 입력을 비웁니다. 입력 오류에는 문구를 보존하고 고칠 곳을 표시합니다.
- 앱 안에서 입력창을 닫거나 이동할 때 미전송 문구가 있으면 버리기·계속 작성을 선택하게 합니다. 같은 계정·회차 안의 임시 초안 보존만 제안하며 브라우저 종료·저장 공간 정리 뒤까지 복원을 보장하지 않습니다.
- 브라우저 뒤로가기·앞으로가기·새로고침·알림에서 돌아오기는 전송이나 확인을 다시 실행하지 않습니다. 상세에서 홈으로 돌아오면 버튼 위치를 유지하고, 요청의 최신 상태만 다시 조회합니다.
- 인증 만료 중에는 초안·이전 본문을 가리고 전송·처리를 중단합니다. 같은 계정으로 재인증하면 허용된 문맥만 복원하고, 계정 교체·로그아웃·권한 회수 때는 사용자별 초안·미전송 문구·캐시를 정리합니다.
- 송신 결과 불명인 작업의 복구 식별자는 본문 없이 해당 계정에 분리해 남길 수 있습니다. 같은 계정 재인증 후 결과 조회에만 사용하고 다른 계정의 화면·전송에 사용하지 않습니다. 보관·정리 기준은 기술·운영 기획과 맞춥니다.
- 다른 탭에서 계정을 바꾸거나 로그아웃하면 현재 탭도 이전 본문을 가리고 계정 확인 화면으로 전환합니다. 이전 계정의 늦은 응답·실시간 이벤트를 새 화면에 반영하지 않습니다. 화면을 작성한 계정·역할·회차와 서버의 현재 문맥이 다르면 전송·완료·담당 변경을 거절하도록 기술 계약을 둡니다.
- 계정·역할·예배가 바뀌어도 이전 요청을 새 문맥으로 보내지 않습니다. 새로고침·뒤로가기 후에도 권한을 다시 확인하며, 예배가 끝난 뒤에는 허용된 이력 조회 화면만 엽니다.

## 손동작·글자·접근성

- 요청 버튼의 실제 터치 영역은 최소 48 CSS px 높이, 주요 버튼은 64~80 CSS px를 초기 시안으로 제안합니다.
- 인접 버튼 간 간격, 엄지손가락 도달 범위, 홈 화면 제스처 영역은 실제 스마트폰에서 검증합니다.
- “크게/작게”를 색만으로 구분하지 않고 문구를 함께 표시합니다. 색과 아이콘은 보조 정보입니다.
- 본문 16~18 CSS px, 주요 요청 18~22 CSS px를 시안으로 검토하고 사용자의 글자 확대를 허용합니다.
- 보통 글자 대비 4.5:1 이상, 큰 글자 3:1 이상과 200% 글자 확대를 검증 기준에 포함합니다. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- 키보드 초점, Enter/Space 조작, 화면 낭독기에서 버튼 이름과 전송 결과가 이해되는지 확인합니다.
- 상태 변화는 접근성 상태 메시지로 알리되 대화 전체를 매번 읽거나 입력 중 초점을 빼앗지 않습니다.
- 자유 입력창은 사용자가 눌렀을 때만 키보드를 띄우며, 키보드가 보내기·닫기를 가리지 않게 합니다.
- 밝기 조정은 기기 설정을 존중합니다. 어두운 화면에서도 대비를 유지하고 화면 켜짐을 강제하지 않습니다.

## 알림과 화면 상태

| 상황 | 서비스 동작 제안 | 사용자가 보는 의미 |
|---|---|---|
| 인도자가 화면을 보고 있음 | 상태 갱신·받은 응답 표시 | 현재 요청 진행 상황 |
| 화면 잠금·다른 앱 사용 | 허용된 기기로 Web Push 시도 | 새 요청·응답을 열어 확인 |
| 알림 거부·미지원 | 홈에 작은 안내, 재방문 시 이력 복구 | 알림 없이도 요청·조회 가능 |
| 집중 모드·무음 | 기기 정책을 존중하고 앱에서 수신 보장 표시 금지 | 알림이 바로 보이지 않을 수 있음 |
| 방송실이 다른 앱 사용 | 허용된 OS 알림과 미확인 개수 유지 | 수신함으로 돌아와 처리 필요 |
| 연결 끊김 | 연결 안내, 최신 상태 불확실 표시 | 전송 성공이나 확인을 추측하지 않음 |
| 로그아웃·계정 변경 | 이전 계정 알림 구독 연결 해제 | 다른 계정의 요청 내용 노출 방지 |

- 기본 제안은 시각 알림입니다. 소리·진동은 사용자가 예배 전에 선택·점검하며 기기별 동작을 보장하지 않습니다.
- 잠금 화면 푸시는 “새 메시지가 있습니다”처럼 선행 요청·응답 모두에 맞는 최소 내용이 기본 후보입니다. 상세는 인증 후 확인합니다.
- 알림 허용은 용도를 설명한 뒤 사용자가 “메시지 알림 켜기”를 누를 때 요청합니다. [Google Permission UX](https://web.dev/articles/push-notifications-permissions-ux)
- “알림 허용됨”, “알림 테스트를 확인함”, “상대가 요청을 확인함”은 서로 다른 상태로 표시합니다.
- 방송실 접속자는 연결된 계정 수일 뿐, 사람이 화면을 보고 있다는 보증으로 표현하지 않습니다.
- 여러 탭·기기에서 같은 요청을 보더라도 하나의 요청 이력으로 합칩니다. 알림 중복은 발송 정책과 표시 식별자로 줄입니다.
- OS 알림을 지우거나 누른 것만으로 요청을 확인 처리하지 않습니다. 푸시를 놓쳐도 받은 메시지의 확인할 항목과 서버 이력이 남으며, 탭을 바꾸어 돌아오면 현재 상태를 다시 가져옵니다.
- 알림 링크의 내용이 삭제됐거나 현재 계정에 권한이 없으면 “이 메시지를 열 수 없어요”와 현재 수신함 이동을 제공합니다. 다른 계정의 이름·예배·본문을 힌트로 노출하지 않습니다.
- 알림 권한 거부는 로그인 실패가 아닙니다. 다시 받기를 원할 때만 설정 안내·시험 경로를 제공하고, 폰을 넣은 동안 꼭 알아야 하는 선행 요청은 알림 실기기 검증과 대체 연락 없이 지원 완료로 판단하지 않습니다.

## 확인한 플랫폼 제약

- iPhone의 Web Push는 iOS 16.4 이상에서 홈 화면에 추가한 웹 앱이 기준이며, 알림 권한 요청에는 사용자 조작이 필요합니다. 일반 브라우저 탭과 구분합니다. [WebKit 공식 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- iOS 웹 앱 알림에도 집중 모드가 적용됩니다. “허용됨”만으로 즉시 표시·진동·소리를 약속할 수 없습니다. [WebKit Focus 설명](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/#focus-support)
- Mac Safari의 표준 Web Push는 macOS Ventura 이상 환경을 기준으로 소개됐습니다. 실제 방송실 OS·브라우저 버전을 먼저 수집합니다. [WebKit Meet Web Push](https://webkit.org/blog/12945/meet-web-push/)
- WebKit은 수신한 Web Push에 사용자에게 보이는 알림을 요구합니다. 전경 화면이라는 이유로 수신 후 알림을 숨기는 방식은 사용하지 않습니다. [WebKit 2025 설명](https://webkit.org/blog/16535/meet-declarative-web-push/)
- 중복을 줄일 때는 서버가 최근 활동 정보를 참고해 발송 대상을 조절합니다. 활동 정보가 낡았을 가능성을 고려하고 알림 누락·중복 모두 검증합니다.
- 선언형 Web Push도 공식적으로 소개됐지만 모든 대상 기기의 지원을 전제로 채택하지 않습니다. 첫 구현의 호환성은 별도 기술 검증 대상입니다. [WebKit 선언형 Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/)
- 플랫폼 지원 시작 버전은 이 서비스의 최종 최소 지원 버전이 아닙니다. 교회 실제 기기로 범위를 확정합니다.

## 재연결·늦은 응답·오프라인

1. 전송 응답을 받지 못했다면 “접수 여부 확인 중”과 “상태 다시 확인”을 표시하고 같은 작업 식별자로 서버 저장 여부를 먼저 조회합니다. 결과를 모른 채 “안 보냈어요”나 “취소됐어요”로 바꾸지 않습니다.
2. 서버 저장이 확인되면 기존 요청을 복구합니다. 새 요청으로 다시 생성하지 않습니다.
3. 한 번도 송신하지 않은 초안·오프라인 요청은 “아직 보내지 못했어요”로 남기고 사용자가 현재 필요성을 확인해 보내거나 기기에서 버릴 수 있게 합니다. 송신했지만 결과를 모르는 작업과 구분합니다.
4. 연결이 회복됐다는 이유만으로 오래된 미전송 요청을 자동 전송하지 않습니다.
5. 접속 복구·화면 복귀 시 서버의 최신 상태와 누락 이력을 가져옵니다. 화면 캐시는 최신이라고 표시하지 않습니다.
6. 오래된 푸시를 눌러도 현재 요청 상태를 먼저 보여줍니다. “예배 종료”·“이미 처리됨”이면 그 사실을 우선합니다.
7. 푸시 보관 시간과 요청의 처리 상태는 별개입니다. 알림이 만료돼도 이미 접수한 요청을 자동으로 완료 처리하지 않습니다.
8. 예배가 끝나면 새 요청을 막고 이력으로 전환합니다. 종료된 예배의 요청을 다음 예배로 옮기지 않습니다.

취소·확인·완료·담당 변경에도 “변경 중→서버 확정” 흐름을 적용합니다. 응답이 끊기면 변경 결과 확인 중으로 두고 동일 작업을 조회합니다. 재조회·재시도는 중복 행동이 되지 않으며, 확정 전에는 완료 목록으로 옮기지 않습니다.
취소가 거절되면 최신 상태와 이유를 보여줍니다. 이미 완료됐다면 “조정이 완료되어 취소할 수 없어요”와 후속 요청 경로를 제공하고, 권한이 없으면 담당 경로를 안내합니다. 통신 장애는 취소 실패로 단정하지 않습니다.
취소가 먼저 저장됐지만 실제 조정은 이미 이뤄졌다면 취소 상태를 유지하고 담당자가 실제 조정 사실을 답변으로 남깁니다. 종료된 회차에서는 권한 있는 담당자의 운영 기록으로 남기며 새 요청 처리를 재개하지 않습니다.
명령은 연결 복구만으로 자동 재전송하지 않습니다. 결과 조회에서 아직 없다고 나와도 늦게 접수될 수 있으므로 실패 확정으로 표시하지 않습니다. 사용자가 다시 전송을 선택하면 같은 작업 ID를 사용합니다.
송신한 작업을 버리려면 서버가 그 작업의 폐기를 확정해야 합니다. 원본이 먼저 접수됐다면 기존 요청을 보여주고 별도 취소로 이어집니다. 연결이 없어 폐기 여부를 모르면 “취소 여부 확인 중”을 남기며, 확인 없이 새 ID로 같은 요청을 보내지 않습니다.

## 실제 기기 검증과 후속 결정

다음 항목은 앞으로 실행할 검증이며, 통과했다고 보고한 결과가 아닙니다.

- iPhone Safari 일반 탭과 홈 화면 웹 앱에서 로그인 유지, 설치 안내, 권한 허용·거부·철회, 잠금 후 응답을 비교합니다.
