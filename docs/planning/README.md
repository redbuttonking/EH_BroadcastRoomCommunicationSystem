# 방송실–예배인도자 소통 서비스 기획안

작성일: 2026-09-16 · 2차 검토일: 2026-09-17 · 상태: 사용자 요구와 추가 검토를 반영한 기획 제안

예배인도자가 개인 스마트폰에서 미리 준비한 요청 버튼을 누르면, 방송실의 Mac 브라우저에 요청이 도착하고 담당자가 확인·처리 결과를 돌려주는 서비스를 기획한다. 직접 입력하는 메시지는 보조 기능이다. 요청을 보낸 사람과 현재 처리 상태를 짧은 시선 이동으로 확인할 수 있도록 한다.

이 문서는 제품, 화면·알림, 기술·보안, 현장 운영을 각각 검토한 서브에이전트 4개의 결과를 통합하는 문서다. 아래의 **확정 요구**는 사용자 발언에서 가져왔고, **권장안**과 **미정 사항**은 다음 기획에서 검토할 제안이다. 아직 서비스 구현이나 실제 기기 검증을 수행한 것은 아니다.

2차 검토에서는 정상 전송 외에 입장할 예배가 없을 때, 담당자와 연락이 끊겼을 때, 계정이 바뀌었을 때, 전송·취소 결과가 불명확할 때의 흐름을 보완한다. 바뀐 내용과 추가하지 않은 기능의 이유는 [2차 검토·결정 기록](05-review-and-decisions.md)에 정리한다.

## 1. 대화에서 확인한 요구사항

| ID | 확정 요구 | 기획에 반영할 내용 |
|---|---|---|
| C01 | 교회 방송실과 예배인도자 사이의 실시간 소통 | 예배 진행에 필요한 요청과 응답을 주고받는다. |
| C02 | 사용자가 미리 준비한 텍스트 버튼이 주 기능 | 예배 중 버튼 한 번으로 요청하며, 사용자별 버튼을 보존한다. |
| C03 | 타이핑으로 보내는 메시지는 보조 기능 | 기본 화면의 큰 요청 버튼을 가리지 않는 입력 경로를 둔다. |
| C04 | 음성과 영상은 필요하지 않음 | 텍스트 요청과 상태 전달을 기준으로 기술을 선택한다. |
| C05 | 앞서 제안한 요청→방송실 확인·처리→응답 흐름 수용 | 서버 접수와 사람의 확인을 구분하고 양방향 응답을 제공한다. |
| C06 | 누구인지 확인할 수 있는 간단한 로그인 필요 | 이름을 계정과 연결하고 요청자와 처리자를 식별한다. |
| C07 | 인도자는 개인 스마트폰, 방송실은 Mac의 브라우저 사용 | 모바일의 짧은 조작과 PC의 지속적인 요청 확인에 각각 맞춘다. |
| C08 | 버튼 설정 등은 나중에 상세 기획 | 개인별 사전 설정 요구는 유지하되 편집 화면·항목·공유 규칙의 상세는 보류한다. |

웹과 앱으로 사용하고 싶다는 의도는 확인했다. PWA로 먼저 제공할지, 별도 설치형 앱이 필요한지는 아직 확정하지 않았다. 아이디·비밀번호, 관리자 계정 발급, 방송실 개인 계정과 공동 수신함, 푸시 알림도 현재는 권장안이다.

## 2. 첫 버전의 권장 범위

첫 대상은 한 교회로 가정한다. 교회 수, 동시 사용자 수, 예배실 수는 실제 운영 확인이 필요하며 성능이나 수용 인원을 검증한 값으로 제시하지 않는다.

| 구분 | 첫 버전에 제안하는 내용 |
|---|---|
| 계정 | 개인 로그인, 표시 이름, 비밀번호 변경·복구, 계정 비활성화, 기기별 로그아웃 |
| 역할 | 해당 예배의 인도자와 방송실 담당자, 계정·예배를 관리하는 관리자 |
| 예배 참여 | 날짜·회차·연습 여부 표시, 부여된 역할로 참여, 준비·접수 중·종료 상태 구분 |
| 빠른 요청 | 개인별 사전 설정 버튼 불러오기와 전송; 상세 설정 설계는 별도 진행 |
| 응답 | 행동 요청의 확인·조정 결과, 안내의 수신 확인, 짧은 이유·후속 답변 |
| 직접 입력 | 버튼으로 표현하기 어려운 요청·답변 작성 |
| 방송실 수신함 | 공동 요청을 한 명이 맡아 처리, 인계와 담당 부재 시 권한자의 재배정 |
| 연결 복구 | 연결 상태 표시, 서버 저장 기록 복구, 중복 요청 방지, 미전송·결과 불명 표시 |
| 알림 | 화면 내 표시를 기본으로 하고, 모바일 푸시·Mac 알림은 지원 기기에서 검증 |

버튼 개인화는 원래 요구사항이므로 최종 첫 버전에서 빠뜨리지 않는다. 설정 기획 전의 기술 검증에서는 임시 기본 버튼을 사용할 수 있지만, 이를 사용자별 사전 설정 기능을 완성한 것으로 간주하지 않는다.

장비를 직접 제어하는 기능, 음성·영상, 파일 전송, 여러 교회를 운영하는 플랫폼, 상세 통계는 이번 첫 버전 범위에 넣지 않는 안을 제안한다. 지금 만드는 버튼은 방송실에 요청을 전달하며 음향 장비나 에어컨을 자동 조작하지 않는다.

## 3. 실제 사용 흐름

1. **처음 사용할 때:** 개인 계정으로 로그인하고 자신의 이름을 확인한다. 인도자는 홈 화면 설치와 알림 사용 여부를 선택한다. 알림을 허용하지 않아도 화면을 열어 요청과 응답을 확인할 수 있게 한다.
2. **예배 전에:** 방송실 담당자가 예배를 준비하고 담당자로 참여한다. 인도자는 날짜·회차를 확인해 참여하고, 본인의 요청 버튼과 연결 상태를 확인한다. 연습용 요청은 실제 예배 요청과 구분한다.
3. **요청할 때:** 인도자가 휴대폰을 꺼내 버튼을 누른다. 받는 대상은 기본적으로 해당 예배의 방송실로 정해 두고, 매 요청마다 상대를 다시 찾게 하지 않는다.
4. **방송실에서:** 요청자·내용·시간을 보고 담당자가 `확인했어요`를 누른다. 이때 담당자가 정해지고 다른 담당자 화면에도 표시된다. 두 사람이 동시에 누르면 서버가 한 명을 정하고 나머지 화면에 현재 담당자를 알린다.
5. **처리한 뒤:** 담당자가 `조정했어요` 또는 이유를 포함한 `처리할 수 없어요`를 보낸다. 인도자는 화면이나 허용된 알림으로 응답을 확인하고 필요하면 `이제 괜찮아요` 또는 추가 설명을 보낸다.
6. **방송실이 먼저 연락할 때:** 해당 예배의 특정 인도자를 선택해 요청이나 안내를 보낸다. 인도자의 명시적 확인도 기록한다.
7. **예배가 끝나면:** 새 요청 접수를 닫고 미처리 요청을 완료와 구분해 남긴다. 다음 예배에는 새 회차로 참여하고 지난 요청을 다시 전송하지 않는다.

예배 회차의 운영 상태는 아래처럼 제안한다. ‘진행’은 실제 예배 순서의 시작이 아니라 **요청 접수가 열려 있음**을 뜻하므로, 예배 전 실제 모니터 조정부터 열어 둘 수 있다. 연습 회차는 별도로 구분한다.

| 회차 상태 | 가능한 행동 | 경계 규칙 |
|---|---|---|
| 준비 | 허용된 사용자의 참여·조회·사전 준비 | 실제 요청 전송은 접수를 연 뒤 가능 |
| 진행·접수 중 | 새 요청·안내·답변, 확인·조정·취소·인계 | 매 동작에 해당 회차 권한 검사 |
| 종료 | 권한과 보관 정책 범위에서 이력 조회 | 새 요청·답변·상태 변경 차단, 재개 기능은 후속 검토 |

입장할 예배나 권한이 없으면 이유와 담당자 문의·목록 새로고침 경로를 보여 준다. 저장한 버튼이 없을 때는 설정 진입과 보조 직접 입력 경로를 제공하되, 개인 버튼을 마련하지 않은 상태를 준비 완료로 보지 않는다.

휴대폰을 다시 열었을 때 로그인과 예배 참여가 유효하면 바로 요청 화면으로 돌아오게 한다. 참여 중이던 예배가 끝났거나 권한이 사라졌다면 그 사실을 알리고 다음 참여 화면으로 이동한다. 화면이 켜져 있다는 사실만으로 방송실의 메시지를 사람이 확인했다고 처리하지 않는다.

완료 후 추가 조정이 필요하면 원 요청에 연결된 새 요청을 만드는 안을 권장한다. 이전 조정 기록은 그대로 남고 방송실에는 새로 할 일이 드러난다. `이제 괜찮아요` 같은 단순 피드백은 원 요청 아래에 붙인다. 인도자는 방송실에서 먼저 보낸 요청도 `받은 메시지`에서 확인하며, 자신이 먼저 요청을 보내지 않아도 이 경로를 사용할 수 있다.

요청 취소는 기록을 지우거나 실제 장비 조작을 되돌리는 기능이 아니다. 조정 중 취소되면 담당자에게 취소 사실을 알리고, 이미 완료됐다면 변경을 위한 새 요청을 보낸다. 취소와 완료가 겹치면 먼저 저장된 변경을 기준으로 최신 상태를 보여 주며, 뒤에 들어온 변경으로 덮어쓰지 않는다.

취소가 먼저 저장됐더라도 담당자가 이미 장비를 조정했을 수 있다. 이때 취소 상태는 유지하고, 회차가 진행 중이면 ‘취소 확인 전에 조정함’이라는 사실을 답변으로 남긴다. 회차 종료 뒤에는 읽기 전용 원칙을 유지하고 현장 운영 기록에 정정 사실을 남긴다.

`처리할 수 없어요`는 사유를 남기고 요청을 처리 불가로 종료하는 응답이다. 잠시 기다리면 처리할 예정인 경우는 직접 답변으로 설명하고 처리 중 상태를 유지한다.

## 4. 서로 구분해야 하는 상태

| 구분 | 의미 | 화면에서 지켜야 할 점 |
|---|---|---|
| 전송 중 | 현재 요청을 서버에 접수하는 중 | 성공 표시를 미리 하지 않는다. |
| 서버 접수 | 서버가 요청을 저장함 | 방송실 사람이 봤다는 의미로 쓰지 않는다. |
| 담당자 확인 | 담당자가 직접 확인 동작을 함 | 담당자 이름과 확인 시간을 함께 남긴다. |
| 조정 완료 | 담당자가 조치를 마쳤다고 알림 | 요청자가 실제 효과를 확인한 것과 구분한다. |
| 확인 완료(안내) | 수신자가 확인만 필요한 안내를 명시적으로 확인함 | 추가 조정 완료를 요구하지 않고 안내 처리를 끝낸다. |
| 요청자 피드백 | 요청자가 괜찮아졌는지 답함 | 응답을 강제로 요구하지 않고 선택적으로 제공한다. |
| 종료 사유 | 취소·처리 불가·예배 종료 등 | 조정 완료와 구분하고 사유를 보존한다. |

행동 요청은 `미확인 → 담당자 확인·처리 중 → 조정 완료 또는 처리 불가`, 단순 안내는 `미확인 → 확인 완료`로 구분한다. 인도자가 빠른 버튼을 누를 때마다 종류를 다시 선택하는 단계는 추가하지 않는다. 직접 입력은 보낼 내용의 목적에 맞는 경로에서 작성한다.

전송 실패와 접수 여부 불명도 구분한다. 서버가 저장한 직후 응답만 끊길 수 있으므로 접수 여부 불명일 때는 같은 작업 ID(전송 시도에 붙이는 고유값)로 저장 여부부터 확인한다. 같은 시도를 다시 조회하거나 전송해도 요청이 중복 생성되지 않게 한다.

조회에서 결과가 없다는 이유만으로 실패가 확정되지는 않는다. 처음 보낸 데이터가 나중에 도착할 수 있기 때문이다. 첫 버전에서는 오래된 변경 명령을 자동 재전송하지 않고, 같은 작업 ID로 재시도하거나 서버에서 해당 시도의 폐기가 확인된 뒤 새로 보낸다. 이미 접수됐다면 요청 취소 절차를 따른다. 로컬 초안을 지우거나 화면을 닫는 동작은 서버 취소와 다르다.

연결이 끊긴 상태에서 새로 누른 요청은 미전송으로 표시하고, 복구 후 사용자가 지금도 필요한지 확인해 전송하는 안을 권장한다. 이미 서버에 저장된 요청을 다시 가져오는 복구 작업과, 저장되지 않은 옛 요청을 뒤늦게 새로 보내는 동작은 다르게 다룬다.

서버가 예배 진행 상황을 추정해 요청의 실제 유효성을 판단하지는 않는다. 늦게 도착했거나 오래 미확인으로 남은 요청은 요청 시점과 접수 시점을 확인하고, 방송실이 현재도 필요한 조정인지 재확인한다. 응답이 없다는 이유로 자동 완료하거나 새 요청을 반복 생성하지 않는다.

## 5. 화면 구성 방향

인도자 화면은 현재 예배·방송실 연결 상태, 큰 요청 버튼, 최근 요청 상태, 받은 메시지, 보조 입력으로 구성한다. 버튼의 위치를 예배 중 자동으로 바꾸지 않고, 색상과 함께 짧은 글자를 사용한다. 화면을 다시 열면 마지막 화면만 믿지 않고 서버의 현재 상태를 확인한다.

‘새 메시지’ 표시는 아직 화면에서 보지 않은 내용을 알려 주고, ‘확인 필요’는 명시적인 사람 응답이 필요한 요청·안내를 뜻한다. 받은 메시지를 열었다는 이유로 담당자 확인을 대신하지 않는다. 확인·완료·취소·담당 변경도 서버 저장 결과가 확인되기 전에는 성공으로 표시하지 않는다.

방송실 화면은 미확인, 처리 중, 처리 결과를 나누고 요청자·시간·담당자가 보이게 한다. 새 요청이 와도 조작 중인 카드가 갑자기 이동하지 않도록 한다. 브라우저가 다른 작업 뒤에 가려졌을 때의 알림과, 화면으로 돌아왔을 때 미확인 요청을 찾는 동작을 함께 검증한다.

화면 구조와 예외 문구는 [화면·알림 검토](02-screens-and-notifications.md)에 정리한다. 이는 버튼 설정 화면을 확정하는 설계가 아니다.

## 6. 로그인과 접근 범위

권장 초기안은 관리자가 사용자를 등록·초대하고 개인 아이디·비밀번호로 로그인하는 방식이다. 표시 이름, 로그인 식별자, 역할은 분리한다. 개인 스마트폰에는 로그인 유지 선택을 제공하고, 공용 Mac에서는 교대 담당자의 계정과 로그아웃 흐름을 확인한다. 로그인 유지 기간과 계정 복구 절차의 세부값은 미정이다.

방송실은 공동 수신함을 사용하되 처리 기록은 개인 계정에 연결한다. 인도자는 자기 요청·응답과 자신에게 전달된 안내를 보고, 방송실 담당자는 자신이 담당하는 예배의 요청을 본다. 관리 권한이 있다는 이유로 모든 대화 열람 권한까지 자동으로 부여하지 않는다.

첫 버전은 한 사람이 한 회차에서 하나의 운영 역할을 맡는 안을 제안한다. 다른 회차에서는 다른 역할을 맡을 수 있고 계정 관리 권한은 별개다. 역할은 권한자가 부여하며, 사용자가 화면에서 역할을 골랐다는 이유로 접근 권한이 생기지 않는다. 같은 회차의 역할 변경은 맡은 요청의 인계와 이전 구독 정리를 거친다. 실제로 동시 두 역할이 필요하다면 이 제한을 개발 전에 재검토한다.

화면에서 숨기는 것에 그치지 않고 서버가 계정 상태, 예배 참여, 수신 대상, 수행 가능한 동작을 검사해야 한다. 계정을 비활성화하거나 역할을 회수하면 기존 연결에서도 새 요청·열람과 새로운 알림 발송이 중단되도록 설계한다. 이미 전달한 알림이나 사람이 본 내용까지 회수할 수 있다고 약속하지 않으며, 잠금 화면에는 최소 내용만 싣고 열 때 권한을 다시 확인한다. 구체적인 인증 처리와 저장 정책은 [기술·보안 검토](03-architecture-and-security.md)를 따른다.

공용 Mac의 다른 탭에서 계정이 바뀌면 이전 화면의 요청 버튼이 새 계정으로 전송되지 않게 해야 한다. 화면이 준비된 계정·회차·역할 문맥과 현재 서버 세션이 다르면 변경을 거절하고 현재 화면을 다시 불러온다. 계정 교체 시 이전 초안·미전송 내용·조회 결과를 비우고, 같은 계정으로 재인증한 경우에만 남은 전송 결과를 확인해 이어 간다.

결과가 불명인 작업은 본문 없이 최소 식별자만 원 계정별로 격리 보존하는 예외를 둔다. 다른 계정에서는 사용하지 않고 원 계정 재인증 후 서버 결과를 조회한다. 브라우저 데이터 삭제나 앱 재설치 뒤까지 이 로컬 식별자를 복구한다고 보장하지 않는다. 로그아웃이나 앱 삭제가 서버에 보낸 요청의 취소를 뜻하지는 않는다.

## 7. 기술 방향과 모바일 알림

권장 구조는 반응형 웹/PWA, HTTPS API, Socket.IO, 데이터베이스를 가진 작은 단일 서비스로 시작하는 것이다. 요청과 상태 변경은 서버에서 검증·저장한 후 응답하고, Socket.IO로 접속 중인 화면에 변경을 전달한다. 푸시는 휴대폰을 내려놓은 동안의 보조 알림으로 사용하며 실제 요청 상태는 데이터베이스를 기준으로 한다.

mediasoup은 실시간 미디어 전송과 DataChannel을 지원하지만, 이번의 텍스트 요청·상태 전달에는 별도 미디어 계층이 필요하지 않다는 판단이다. 공식 문서에서도 일반 메시지를 별도 WebSocket 등의 통신 경로로 교환할 수 있다고 설명한다. [mediasoup 공식 문서](https://mediasoup.org/documentation/v3/communication-between-client-and-server/)

Socket.IO의 자동 재연결만으로 메시지 누락을 막을 수는 없다. 서버 저장, 요청 고유 ID, 재접속 후 상태 조회를 함께 구현하는 안을 채택한다. [Socket.IO 전달 보장](https://socket.io/docs/v4/delivery-guarantees/)

아이폰 웹 푸시는 iOS 16.4 이상에서 홈 화면에 추가한 웹 앱과 사용자 알림 허용이 필요하다. 집중 모드 등의 영향을 받으므로 조용한 진동이나 즉시 도착을 서비스가 보장하는 표현을 사용하지 않는다. PWA 선택은 실제 사용할 아이폰·안드로이드와 Mac 브라우저의 설치·알림 실험을 거친 뒤 확정한다. [Apple WebKit 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

예배가 끝났거나 취소된 요청의 알림을 눌렀다면 최신 종료 상태를 보여 준다. 푸시 알림 자체를 요청 처리 명령이나 담당자의 확인으로 간주하지 않는다.

## 8. 현장 검증과 개발 순서

구현에 앞서 통신 환경과 실제 기기의 제약을 검증하고, 기능 개발 뒤에는 모의 예배를 거쳐 제한된 실제 예배에서 시험하는 순서를 권장한다. 구체적인 운영 절차와 도입 판단 기준은 [현장 운영 검토](04-operations-and-validation.md)에 정리한다.

방송실 담당자의 온라인 표시와 실제 대응 가능 여부는 다르다. 당일 수신을 맡을 사람과 교대 절차를 정하고, 서비스가 끊겼을 때 사용할 대체 연락 방법도 리허설에서 확인한다. 담당자가 잠깐 접속을 잃었다는 이유로 맡은 요청을 자동 해제하지 않는다.

담당자가 복귀하지 못하거나 권한을 잃어 인계할 수 없다면, 해당 회차의 재배정 권한을 가진 방송실 책임자가 실제 장비 조정 여부를 확인하고 사유와 새 담당자를 기록한다. 정상 인계와 책임자 재배정을 구분하며 자동으로 중복 작업을 지시하지 않는다.

방송실 Mac이 자막·송출·녹화에도 사용된다면 서비스 화면과 OS 알림이 성도용 화면·녹화·송출 오디오에 노출되는지 실제 출력 경로로 점검한다. 기본은 화면 내 표시로 두고 추가 알림은 현장 검증을 거쳐 선택한다.

개인 스마트폰이 교회 Wi-Fi와 이동통신을 오가야 한다면 외부에서 접속 가능한 HTTPS 주소를 제공하는 클라우드 구성을 우선 검토한다. 교회 내부망 전용 서버는 이동통신에서 접근하는 경로, HTTPS, 전원과 복구 담당자를 별도로 마련해야 한다. 내부 서버를 쓰더라도 외부 푸시 서비스가 인터넷 없이 동작한다고 가정하지 않는다.

예배 중 배포·자동 새로고침을 피하고 백업 생성과 실제 복구 시험을 구분한다. 화면을 열어 둔 실험의 성공만으로 잠금 상태 알림과 현장 운영까지 준비됐다고 판단하지 않는다.

정상 서버 재시작과 과거 백업 복원은 다르게 다룬다. 과거 백업에는 최근 요청·취소·권한 회수가 빠질 수 있으므로, 복원 직후 쓰기와 알림을 막고 현장 기록을 대조한다. 복원된 진행 회차를 마감하고 권한·세션·삭제 내역을 정리한 뒤, 계속 사용할 때는 새 회차 ID로 시작한다. 복원된 옛 탭이나 알림으로 과거 작업을 다시 실행하지 않는다.

권한 명단 확인과 삭제 내역 확인은 별개다. 삭제 여부가 불명인 복원 본문은 비공개로 유지하고 보관 정책에 따라 정리한다. 복구된 데이터를 전부 다시 공개하는 것을 기본값으로 두지 않는다.

| 단계 | 작업 | 다음 단계로 넘어갈 근거 |
|---|---|---|
| 1. 요구 확인 | 로그인·참여·알림·운영 책임자와 최소 설정 범위 결정 | 미정 사항의 선택과 이유가 기록됨 |
| 2. 기술 검증 | 실제 스마트폰↔Mac 전송, 잠금·앱 전환·재연결·알림 실험 | 지원 범위와 제한이 실제 기기로 확인됨 |
| 3. 핵심 기능 | 로그인, 예배 참여, 개인별 버튼, 요청·응답, 저장·복구 | 핵심 수용 시나리오 통과 |
| 4. 모의 예배 | 여러 요청, 담당자 교대, Wi-Fi 전환, 미처리 종료 실습 | 누락·중복·오해·조작 실수 결과 기록 |
| 5. 제한 도입 | 정한 예배에 먼저 적용하고 현장 피드백 수집 | 담당자가 운영 가능하고 남은 문제가 수용 가능한지 판단 |

정확한 일정과 비용은 사용자 수, 운영 인력, 호스팅·DB·백업 선택을 확인한 뒤 산정한다. 이번 문서의 단계는 일정 약속이나 성능 측정 결과가 아니다.
