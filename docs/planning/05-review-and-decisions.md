# 2차 검토·결정 기록

검토일: 2026-09-17 · 대상: 1차 통합안과 제품·화면·기술·운영 기획서

사용자의 요청에 따라 같은 4개 관점의 서브에이전트가 현재 문서를 다시 읽고 누락, 모순, 추가 기능의 필요성을 검토했다. 아래 ‘반영’은 **기획 문서를 수정했다는 뜻**이며, 서비스 구현이나 실기기 시험을 완료했다는 뜻은 아니다. 새 정책은 사용자 확정 요구가 아닌 권장안으로 유지한다.

## 1. 변경하지 않은 요구

- 예배인도자는 개인 스마트폰을 잠깐 꺼내 쓰고, 방송실은 Mac 브라우저로 소통한다.
- 사용자별 사전 요청 버튼이 주 기능이고 직접 입력은 보조 기능이다.
- 로그인으로 요청자와 담당자를 구분하고 요청·확인·처리 결과를 양방향으로 주고받는다.
- 음성·영상은 현재 범위에 포함하지 않는다.
- 버튼 설정의 상세 UI는 다음 기획에서 다룬다. 개인 버튼 생성·수정·보존 요구를 첫 버전에서 없애지는 않는다.
- PWA·Socket.IO·아이디/비밀번호·관리자 계정 발급은 검토 중인 기술·운영 제안이다.

## 2. 이번에 수정·보완한 결정

### R01. 예배 회차의 상태와 입장 권한

기존에는 ‘예배 종료 뒤 새 요청 금지’만 분명했고 준비 중 요청이나 입장 권한 부여가 불명확했다. 준비는 허용된 참여·조회, 진행은 요청 접수 열림, 종료는 권한 범위의 조회만 허용하는 안으로 정리했다. 진행 상태는 실제 예배 시작 전에도 열어 모니터 조정을 요청할 수 있다. 연습은 별도 회차다.

회차별 역할은 권한자가 부여한다. 첫 버전은 한 사람·한 회차에 한 운영 역할을 제안하되 실제로 동시 두 역할이 필요하면 개발 전에 재검토한다. 계정 관리 권한은 별도이며 메시지 열람 권한을 자동으로 주지 않는다. [제품 2~3절](01-product-and-workflows.md), [통합안 3·6절](README.md)

### R02. 행동 요청·안내·답변의 처리 규칙

기존 화면은 ‘안내는 확인으로 종료’를 제안했지만 제품 상태와 데이터 모델의 구분이 충분하지 않았다. 행동 요청은 확인 후 조정 완료·처리 불가로, 안내는 수신자의 명시적 확인으로 끝나도록 맞췄다. 기존 요청에 대한 답변에는 새 담당 배정이나 완료 동작을 요구하지 않는다.

빠른 요청 버튼은 한 번 누르는 흐름을 유지한다. 요청·안내 종류를 매 전송마다 고르게 하지 않고 진입 경로와 기본값으로 정한다. [제품 4~5절](01-product-and-workflows.md), [화면 여정](02-screens-and-notifications.md), [기술 3~4절](03-architecture-and-security.md)

### R03. 시작하지 못하는 화면과 실패 뒤의 다음 행동

계정 없음, 초대 만료, 권한 없음, 예배 없음, 버튼 없음, 목록 조회 실패, 상대 부재에서 사용자에게 보여 줄 내용과 다음 행동을 추가했다. 빈 목록과 통신 실패는 구별한다. 인증 만료 뒤 같은 계정으로 돌아와도 이전 전송·확인·완료를 자동 실행하지 않는다.

버튼이 없는 사람에게 설정·직접 입력 경로를 제공하지만, 개인 버튼을 준비하지 않은 상태를 사전 설정 기능 완성으로 간주하지 않는다. [화면의 시작 불가·이동 규칙](02-screens-and-notifications.md)

### R04. 담당자 이탈과 실제 장비 조정 사실

기존 담당자가 돌아오지 못하면 정상 인계만으로 진행 중 요청을 넘길 수 없었다. 해당 회차의 재배정 권한을 가진 방송실 책임자가 실제 작업 상황을 확인하고 사유와 새 담당자를 남기는 절차를 추가했다. 잠깐 접속이 끊겼다는 이유로 자동 담당 해제를 하지는 않는다.

취소와 완료가 겹치면 먼저 저장된 상태를 유지한다. 취소가 먼저 저장됐어도 실제 조정이 끝났다면 그 사실을 진행 회차의 답변에 남긴다. 회차 종료 뒤에는 현장 운영 기록으로 남기며, 기록을 남기기 위해 종료된 회차를 다시 열지는 않는다. [제품 6절](01-product-and-workflows.md), [기술 7절](03-architecture-and-security.md), [현장 운영](04-operations-and-validation.md)

### R05. 접수 여부 불명과 재전송·폐기

서버 조회에 결과가 아직 없다는 사실만으로 미접수를 확정할 수 없었다. 처음 보낸 데이터가 늦게 도착하는 경우를 포함해 동일 작업 ID로 조회·수동 재시도하도록 보완했다. 보내기를 포기한다면 서버에서 해당 시도의 폐기가 확정돼야 새 시도와 구분할 수 있다. 이미 접수됐다면 기존 요청의 취소 절차를 따른다.

별도 전송 만료 토큰과 자동 명령 재시도를 첫 버전의 필수 설계로 두지 않고, 결과 조회와 명시적인 재시도·폐기를 기준으로 단순화했다. 서버의 실시간 이벤트 전달 재시도는 새 요청 명령을 재실행하는 것과 다르다. 실제로 필요가 없어진 오래된 요청인지는 방송실이 진행 상황을 재확인한다. [기술 5~6절](03-architecture-and-security.md), [화면의 재연결 규칙](02-screens-and-notifications.md)

### R06. 공용 Mac의 계정 교체와 옛 화면

다른 탭에서 계정이 바뀌면 오래된 화면의 버튼이 새 계정으로 실행될 수 있는 틈을 막도록 기획했다. 화면을 준비한 계정·회차·역할 문맥과 현재 서버 문맥이 다르면 전송·완료·담당 변경을 거절한다. 계정 교체 후 늦게 도착한 이전 응답도 새 화면에 반영하지 않는다.

본문·초안·화면 캐시는 정리하되 결과가 불명인 작업의 최소 식별자만 원 계정별로 격리해 남기는 예외를 둔다. 원 계정 재인증 후 서버 결과 조회에 사용하며, 다른 계정에서 표시·재시도하지 않는다. 로그아웃은 이미 보낸 요청을 취소하는 동작이 아니다. [화면의 계정 교체 규칙](02-screens-and-notifications.md), [기술 9절](03-architecture-and-security.md)

### R07. 받은 메시지 숫자와 설치 후 복귀

‘새 응답’과 ‘명시적인 확인이 필요한 요청·안내’를 분리한다. 상세를 열거나 OS 알림을 지웠다고 상대에게 사람 확인을 기록하지 않는다. 확인한 행동 요청은 처리할 목록에 남고 안내는 확인 완료로 끝난다.

브라우저에서 홈 화면 앱으로 이동하거나 앱을 재설치할 때 로그인·알림 구독이 자동으로 이어진다고 가정하지 않는다. 실제 기기에서 각각 확인하고 필요한 로그인·알림 점검 경로를 제공한다. [화면·알림 기획](02-screens-and-notifications.md)

### R08. 최소 데이터와 보관 경계

개인 버튼, 요청에 연결된 답변, 요청·안내 종류를 기술 모델에서 빠뜨리지 않도록 했다. 버튼을 수정해도 과거에 보낸 문구는 바뀌지 않는다. 버튼 편집 화면의 상세나 공유·분류 방식은 여전히 보류한다.

동일 작업의 적용·폐기 기록을 너무 빨리 지우면 늦은 재시도가 새 요청으로 실행될 수 있으므로, 진행 중인 회차의 기록은 중복 방지에 필요한 동안 유지한다. 종료·보관 만료 뒤에는 새 실행을 허용하지 않고 회차 ID를 재사용하지 않는다. 보관 기간과 최소 식별정보의 정리는 도입 전에 운영 정책으로 결정하며 무조건 영구 보관하지 않는다. [기술 데이터·복구 규칙](03-architecture-and-security.md), [운영의 보관 정책](04-operations-and-validation.md)

### R09. 정상 재시작과 과거 백업 복원

정상 재시작은 남아 있는 저장 기록을 다시 읽는 동작이지만, 과거 백업을 복원하면 최근 접수·취소·권한 회수 기록이 없을 수 있다. 같은 복구 절차로 자동 재개하지 않도록 분리한다.

과거 백업 복원 직후에는 전송을 막고 기존 로그인 세션·권한·삭제 내역을 재검토한다. 복원된 진행 회차는 현장 대조 후 복구 사유로 마감하며, 계속 소통하려면 새 회차 ID로 명시적으로 시작한다. 옛 요청·알림을 자동 이월하지 않는다. [기술 배포·복구](03-architecture-and-security.md), [현장 복구·검증](04-operations-and-validation.md)

권한 명단을 다시 확인하는 것만으로 과거 삭제 여부까지 알 수는 없다. 삭제 여부가 불명인 본문은 비공개로 유지하고 보관 정책에 따라 정리한다.

### R10. 담당자 부재·계정 복구와 검증 범위

분실한 휴대폰의 세션 회수, 비밀번호 분실·초대 만료, 관리자 부재, 무응답 시 대체 연락을 누가 처리할지 운영 절차에 추가했다. 다른 사람의 계정이나 공용 비상 관리자 계정으로 우회하지 않고, 지정된 개인 계정의 대체 담당자 또는 현장 대체 연락을 이용한다.

기존 O01~O14를 보완하고 O15~O24를 추가해 검증 계획을 24개 시나리오로 확장했다. 기기·계정·회차·작업 ID와 기대 결과를 함께 기록하도록 했다. 이는 검증 계획이며 아직 실제 서비스의 통과 결과는 없다. [운영 2·6·8~9절](04-operations-and-validation.md)

## 3. 검토했으나 첫 버전에 추가하지 않은 기능

| 항목 | 지금 추가하지 않는 이유 | 다시 검토할 조건 |
|---|---|---|
| 접속 끊김에 따른 자동 담당 해제 | 실제 장비 작업이 진행 중일 수 있음 | 명시적 인계만으로 운영이 어려운 사례가 확인됨 |
| 반복 재촉·자동 긴급 알림 | 예배 방해와 같은 요청의 중복 조정을 늘릴 수 있음 | 무응답 시 대체 연락만으로 부족함을 현장에서 확인 |
| 종료 회차 재개 | 과거 작업·알림이 현재 요청과 섞이기 쉬움 | 기록 정정 이상의 실제 재개 요구가 있음 |
| 한 회차에서 한 사람의 동시 복수 역할 | 화면·알림·열람 권한의 경계를 복잡하게 함 | 같은 예배 중 동시 역할 수행이 실제로 필요함 |
| 자동 서버 이중화·별도 메시지 브로커 | 현재 확인된 한 교회 운영 범위에 비해 관리 요소가 늘어남 | 복구 목표와 규모가 단일 서버로 충족되지 않음 |
| 상세 버튼 편집·공통 배포 규칙의 지금 확정 | 사용자가 상세 설정 기획을 나중에 하기로 함 | 설정 기획 단계에 들어감; 최소 개인 기능은 그대로 유지 |

## 4. 다음 단계에서 사용할 시작안

아래는 미정 항목을 진행시키기 위한 기본 제안이며 승인된 최종 사양이 아니다.

| 결정 | 시작안 | 먼저 확인할 현장 정보 |
|---|---|---|
| 계정 등록 | 관리자가 개인 계정을 등록·초대하고 본인이 인증 정보를 설정 | 계정 발급·복구를 맡을 사람과 대체 담당자 |
| 예배 진입 | 허용된 회차 목록에서 날짜·역할을 확인 후 참여 | 동시 예배실·같은 회차 복수 역할 필요성 |
| 제공 방식 | 반응형 웹/PWA로 실제 폰·Mac 동작 먼저 검증 | 아이폰/안드로이드·Mac 버전, 설치·알림 사용 의사 |
| 서버 위치 | Wi-Fi·이동통신에서 같은 주소로 접근 가능한 클라우드 우선 검토 | 교회 회선, 대체 연락, 서버·복구 운영 가능 시간 |
| 첫 현장 사용 | 별도 연습 후 한 실제 회차에서 제한 도입 | 수신 담당자, 무응답 전환 기준, 보관·복구 목표 |
