# 프로젝트 통합 규정·결정 기준

정리일: 2026-10-10. 대화, 프로젝트 문서·코드·설정과 GitHub 읽기 검토에서 확인한 38개 분야를 통합했다. [프로젝트 AGENTS.md](../AGENTS.md)와 함께 적용한다. 이 문서 작성은 프로그램 변경·배포나 검증 재실행을 의미하지 않는다.

## 읽는 기준

- 원칙: 사용자와 합의한 제품·작업 기준이다. 최신 명시적 사용자 결정이 우선한다.
- 현재 구현: 정리 시점의 코드·설정에서 확인한 방식이다. 숫자와 도구 선택까지 모두 영구적인 사용자 정책이라는 뜻은 아니다.
- 관례: 사용해 온 방식이며 자동 강제나 별도 확정 여부를 구분한다.
- 폐기·미정: 과거 검토나 후속 결정으로 제외한 내용이다. 새 구현 지시나 필수 개발 목록으로 취급하지 않는다.

합의된 정책을 바꾸면 AGENTS와 이 문서의 관련 항목, README·운영 안내를 함께 갱신한다. 현재 구현의 세부값이 달라지면 해당 값을 검증하고 이 문서도 맞춘다. 과거 기록에 적힌 값·검증 결과를 최신 사실로 옮기지 않는다. 1~9차 대화 원문 전체가 개별 문서로 보존됐다는 근거는 확인하지 못했으므로, 이 문서는 확인 가능한 자료의 통합 기준이다.

## 1. 기획과 개발의 결정 기준

- 최신 사용자 요청·합의를 우선하고 이전 기획과 충돌하면 이후 결정에 따른다.
- 기능·비용·운영 정책을 임의로 확정하지 않는다. 이미 승인된 구현과 검증은 같은 승인을 반복 요청하지 않는다.
- 설명·추천·검토를 요청한 것만으로 파일·설정을 변경하지 않는다. 명확한 작업 요청은 실행한다.
- 요청과 관련된 범위만 수정하고 사용자 변경을 보존한다. 공통 동작은 기존 컴포넌트·유틸리티에 반영한다.
- 현재 동작은 코드·설정·[README](../README.md)를 대조한다. [개발 기록](development.md)의 앞부분과 `docs/planning/`에는 이후 대체된 내용이 있다.

## 2. 서비스 목적과 범위

- 교회 내부에서 예배인도자와 방송실이 예배 흐름을 방해하지 않고 소통하는 도구다. 판매용 다중 교회 플랫폼으로 임의 확장하지 않는다.
- 준비한 문구 버튼이 주 기능이고 직접 입력은 보조 기능이다. 양쪽 모두 문구와 채팅을 보낸다.
- 방송실 Mac 브라우저와 인도자 개인 스마트폰을 기본 환경으로 보되 역할을 운영체제에 묶지 않는다.
- 음성·영상, 예배 회차, 여러 담당자의 배정·인계·중복 처리 관리는 제외했다.
- 읽음·확인·처리 중·완료·만족 회신을 요구하지 않는다. ‘조정했어요’도 일반 메시지다.
- 요청 문구는 사람에게 전달한다. 마이크·에어컨 등 장비를 직접 제어하지 않는다.

## 3. 기술과 서비스 제공 방식

- 현재 기준은 React·TypeScript·Vite 웹앱/PWA와 Firebase Authentication·Realtime Database·정적 Hosting이다.
- Firestore·Cloud Functions·App Hosting·별도 상시 서버·교회 Mac 서버·mediasoup·WebRTC는 현재 구성에 없다. 현재 구성에 Vercel은 필요하지 않다.
- React Native·WebView 포장·앱스토어 출시는 별도 합의 대상이다.
- 화면·공통 UI·도메인 검증·Firebase 연결을 분리하고 기존 구현을 재사용한다.
- 프로젝트 ID는 `eh-worship-chat`, 관리용 이름은 `EH Worship Chat`, RTDB 지역은 사용자 선택인 싱가포르다.

## 4. 비용

- Firebase 무료 운영이 기본 조건이다. 기존 운영 기록은 결제 계정 없는 Spark 구성이다. 실제 결제·사용량 상태는 확인한 시점과 구분한다.
- 결제 연결·유료 요금제·서비스·에셋 도입이 필요하면 비용과 대안을 먼저 설명하고 사용자 결정을 받는다.
- Firebase 무료 범위에서 어려운 기능은 함께 범위를 조정한다.
- 방 수 제한·나눠 읽기·전송 간격 제한을 유지한다. 이를 프로젝트 전체 사용량 제한이나 무중단 보장으로 설명하지 않는다.
- 운영 사용량 확인과 남은 방 정리는 [운영 안내](firebase-setup.md)의 최신 절차를 따른다. 데이터 삭제가 이미 발생한 다운로드 사용량을 되돌리지는 않는다.

## 5. 회원가입과 로그인

- 홈 카드에서 이메일 로그인·회원가입·비밀번호 재설정 화면을 전환한다. 일반 사용자는 Firebase 콘솔 대신 서비스에서 가입한다.
- 계정 비밀번호는 Authentication이 관리하며 RTDB에 저장하지 않는다. 방 비밀번호와 별개다.
- 현재 구현은 비밀번호 확인·보기/숨기기·자동완성·입력 오류·처리 중 표시·중복 제출 방지를 제공한다. 화면 전환 시 이메일은 유지하고 비밀번호와 오류는 초기화한다.
- 비밀번호 재설정은 가입 여부에 관계없이 같은 확인 안내를 사용하고 한국어 메일을 요청한다. 회원가입 오류까지 모두 같은 문구인 것은 아니며 실제 메일 수신을 자동 검사로 보장하지 않는다.
- 새 접속마다 익명 계정을 만드는 방식은 폐기했다. 기존 익명 레코드를 일괄 삭제한 것은 아니다. 옛 익명 계정의 방 이용은 차단하고 자기 연결 정리만 호환 허용한다.

## 6. 내부 이용 제한과 승인

- 신규·기존 일반 계정은 관리자 승인을 받아야 한다. 관리자도 이메일 인증을 생략하지 않으며 승인된 관리 계정으로 이용한다.
- 미인증·미승인·거절 계정의 방 목록·생성·입장·대화를 화면과 서버에서 차단한다. 미인증 신청 승인을 막는다.
- 승인 대기·승인·거절, 이메일 미인증, 조회 중·실패를 구분한다. 승인 기록이 없으면 대기로 처리한다.
- 관리자는 승인·거절·승인 취소를 확인창으로 처리하고 다시 승인할 수 있다. 승인 취소는 계정 삭제가 아니다.
- 결과는 신청자 화면에 반영한다. 승인 취소 시 방 구독·화면·복원 정보를 정리하고 자기 연결을 해제한다.
- 승인은 서비스 이용 허가다. 미승인 계정도 Authentication에는 만들어질 수 있으므로 계정 생성 자체를 사전 승인한다고 설명하지 않는다.
- 역할별 초대코드와 콘솔에서 고정 계정 두 개를 만드는 방안은 채택하지 않았다.

## 7. 일반 역할과 관리자 권한

- 일반 계정은 가입 시 방송실·예배인도자를 선택하고 임의로 변경하지 않는다. 역할 없는 기존 이메일 계정은 한 번 설정한다.
- 관리자 권한은 방송실 역할과 별개다. 일반 방송실은 가입자를 승인할 수 없다.
- 관리자는 기본 홈에서 시작한다. 헤더의 같은 위치에서 ‘가입 승인 관리’와 ‘기본 홈’을 전환한다.
- 관리자는 새 방 생성 시 방송실로, 기존 방에서는 입장마다 선택한 역할로 참여한다. 이전에 저장한 일반 역할로 제한하지 않는다. 방 안에서 역할을 바꾸지는 않는다.
- 관리자 지정은 신뢰된 관리 작업에서 UID로 처리한다. 클라이언트의 특정 이메일 문자열로 판별하거나 자가 승격·자기 승인 변경을 허용하지 않는다. 관리자 지정 해제 시 일반 역할 제한으로 돌아간다.
- 현재 계정 수를 두 개로 제한하지 않는다. 대화는 개인 실명·이메일 대신 참여 역할을 표시한다.

## 8. 로그인 유지와 중복 접속

- 가능한 환경에서는 브라우저에 로그인을 유지하고, 저장이 막히면 현재 창 메모리만 사용하며 안내한다.
- 방 나가기는 로그아웃이 아니다. 로그아웃은 같은 브라우저의 다른 탭에 반영되며 다른 기기의 로그인은 유지한다.
- 다중 기기 로그인 자체는 허용한다. 같은 방은 역할별 자리와 동일 계정 중복 입장을 제한하며 새 접속이 기존 참여자를 강제 퇴장시키지 않는다.
- 같은 앱 화면에서는 현재 방에서 나온 뒤 다른 방을 생성·입장한다. 계정 전체를 한 기기로 제한하는 정책은 아니다.
- 계정 전환 시 이전 계정의 대화·초안·미전송·구독·방 복원 정보를 정리한다. 관련 없는 기기 설정까지 지우지 않는다.
- 서버의 신원 기준은 UID다. 같은 계정의 기기들은 그 계정이 참여 중인 방에 대해 동일한 계정 권한을 가진다. 중복 입장 차단을 기기 간 보안 격리로 설명하지 않는다.

## 9. 방 생성과 입장

- 방송실 계정과 관리자가 생성한다. 일반 예배인도자는 생성하지 못한다.
- 이름과 비밀번호를 받으며 기본 이름 ‘대화방 6자리 숫자’를 그대로 쓰거나 바꿀 수 있다. 이름과 식별 코드는 별개다. 이전 이름 없는 방에는 코드 기반 표시 이름을 사용한다.
- 목록에서 열린 방을 선택하고 비밀번호로 입장한다. 방 코드는 선행 0을 보존한다.
- 생성 계정당 유지 가능한 방 최대 3개는 사용자가 선택한 정책이다. 기존 방을 자동 삭제하지 않고 닫으면 슬롯을 반환한다.
- 방마다 방송실 1명·예배인도자 1명이다. 인증·승인·역할·비밀번호 검증과 실제 자리 점유를 서버에서 함께 확인한다.
- 현재 연결·자리·입장 알림은 함께 기록한다. 자리를 얻지 못한 계정은 대화를 읽지 못하며 늦은 입장 요청이 종료된 연결을 되살리지 않게 한다.

## 10. 방 소유권과 종료 권한

- 일반 종료는 생성 계정이 방송실로 참여한 상태에서만 허용한다. 생성자는 재입장 후에도 이 조건으로 닫을 수 있다.
- 다른 방송실 계정은 빈 자리에 들어와 대화할 수 있지만 남의 방을 닫지 못한다.
- 관리자도 비밀번호·자리·소유권을 자동 우회하지 않는다. 관리자 생성자가 예배인도자로 들어온 상태에서는 일반 종료 권한을 주지 않는다.
- 예외적으로 관리자는 참여자 없는 방을 정리할 수 있다. 소유자가 승인 취소된 방도 포함한다. 동시에 누군가 입장하면 서버가 현재 참여 상태를 확인해 삭제를 거절한다.

## 11. 방 유지와 삭제

- 생성자 나가기는 ‘방을 유지하고 나가기’와 ‘방을 완전히 닫기’를 제공한다. 비소유 방송실·예배인도자는 나가기만 한다.
- 단절·브라우저 종료·모두 퇴장한 경우에도 방과 기록을 유지한다. 마지막 접속 해제로 방 전체를 삭제하지 않는다.
- 유지된 방 재입장 시 이전 대화와 입퇴장 기록을 보여준다.
- 완전히 닫으면 방 메타·메시지·입퇴장·입장 검증 정보·목록·소유 슬롯을 함께 삭제한다. 일부만 삭제하거나 늦은 쓰기로 되살리는 요청을 차단한다.
- Authentication 계정·프로필·승인·빠른 문구는 별도로 남는다. 닫은 방의 대화를 설정 백업으로 복구할 수 있다고 안내하지 않는다.

## 12. 재접속과 연결 상태

- 연결 중·단절을 작은 상단 안내로 표시하고 다시 연결 경로를 둔다.
- 초점·visibility 변화만으로 퇴장시키지 않는다. 종료 감지에는 지연이 있을 수 있으며 서버가 종료를 확인한 뒤 자리를 재사용한다.
- 종료 정리를 미리 예약하고, 실제 들어오지 못한 연결에 가짜 퇴장 기록을 만들지 않는다. 오래된 비동기 결과·구독이 새 로그인이나 방 화면에 반영되지 않게 한다.
- 새로고침 자동 복원은 인증과 해당 탭의 유효한 sessionStorage 힌트가 있을 때 시도한다. 새 창·재설치 이후 자동 입장까지 보장하지 않는다.
- 복원 힌트는 UID·방 ID·코드이며 비밀번호가 아니다. 명시적 퇴장·종료·계정 전환 시 지운다.
- 상대의 ‘접속 중/연결 대기’는 연결 상태다. 자신의 연결이 끊겼을 때 상대가 온라인이라고 확신하지 않으며, 접속 중을 읽음·조정 완료로 해석하지 않는다.

## 13. 대화 표시와 입력

- 본인 메시지는 오른쪽, 상대는 왼쪽에 역할과 시각을 표시한다. 연속 역할명 반복을 줄이고 역할 전환·이벤트 뒤 다시 표시한다. 본문 줄바꿈은 보존한다.
- 입장·퇴장·연결 끊김은 가운데 알림으로 구분하며 방 유지 중 기록을 남긴다.
- 서버 시각·ID로 정렬하고 동일 시각에는 입장→메시지→퇴장/단절 보조 순서를 사용한다. 실제 누른 시각의 전역 순번 보장은 아니다.
- Enter 전송, Shift+Enter 줄바꿈이다. 한글 조합 중 Enter·반복 키·공백뿐인 입력 전송을 막는다.
- 맨 아래를 보는 중에만 새 메시지로 자동 이동한다. 이전 대화를 읽으면 위치와 ‘새 메시지’ 이동 버튼을 유지한다. 이전 페이지를 불러와도 읽던 위치를 보정한다.
- 상대가 없는 방에도 남아 있는 참여자는 메시지를 보낼 수 있다. 개별 메시지 수정·삭제 기능은 현재 제공하지 않는다.

## 14. 전송 실패와 중복 방지

- ‘전송 중’·‘전송 확인 필요’를 구분한다. 서버 응답이 불명확하다는 이유로 성공이나 미전송을 단정하지 않는다. 상대 읽음 상태와도 구분한다.
- 현재 쓰기는 REST를 사용해 SDK 오프라인 쓰기 큐의 뒤늦은 자동 전송을 피한다. 실시간 수신은 Firebase SDK를 사용한다.
- 같은 전송의 재확인은 같은 ID와 내용으로 처리한다. 같은 ID를 다른 내용·신원으로 덮어쓰지 못하게 한다. 사용자의 의도적인 반복 문구 선택은 새 메시지다.
- 연결 끊김·처리 중 전송을 막고 연타·키 반복·스크롤 손동작에 의한 문구 오발송을 방지한다. 옛 요청을 복구 직후 무조건 다시 보내지 않는다.
- 실패 시 현재 초안을 보존하고 이전 응답이 새로 작성한 문장을 지우지 않게 한다. 생성·저장 결과가 불명확하면 같은 대상의 서버 상태를 재확인한다.
- 채팅 초안·미확정 전송은 메모리 상태다. 새로고침·로그아웃 이후 영구 복구나 일반 채팅 초안 퇴장 확인창은 현재 구현하지 않았다.

## 15. 빠른 문구의 저장·편집 범위

- Firebase에 계정·역할별로 저장하고 다른 환경에도 반영한다. 방 종료·브라우저 데이터 삭제로 계정 문구를 지우지 않는다.
- 홈 ‘내 빠른 문구’와 방 안 편집에서 같은 편집기를 사용한다. 방 안에서는 참여 역할을 편집한다.
- 일반 사용자는 자신의 역할, 관리자는 자신의 두 역할 문구를 각각 편집한다. 다른 사용자의 문구는 관리자도 접근하지 못한다.
- 추가·수정·삭제·순서 변경을 지원하며 분류는 제거했다.
- 저장 목록이 없을 때 기본 문구를 제공한다. 인도자는 모니터·마이크·온도·괜찮음·잘못 보냄의 5개, 방송실은 조정·기다림·상태 질문·잘못 보냄의 4개가 현재 기본값이다. 고정 업무 절차가 아니다.
- 빈 문구는 저장하지 않되 전체 목록을 비우는 것은 허용하고 유지한다. 문구를 고쳐도 이미 보낸 메시지는 바뀌지 않는다.
- 기존 기기 문구는 ‘이 기기 문구 가져오기’를 선택하고 저장할 때만 옮긴다. 공유 기기의 설정을 새 로그인 계정에 자동 복사하지 않는다.

## 16. 빠른 문구 편집의 사용성

- 위아래 화살표·오른쪽 손잡이 드래그·키보드 정렬을 함께 제공한다. 입력 선택이나 일반 스크롤을 드래그로 해석하지 않는다.
- 키보드는 Space 잡기/놓기, 방향키 이동, Escape 취소를 지원한다. 첫 항목 위·마지막 항목 아래는 비활성화한다.
- 이동한 카드에 부드러운 한 번의 테두리 펄스와 위치 안내를 주고 필요한 스크롤을 맞춘다. 모션 감소 설정에는 정적 강조를 쓴다.
- 제목·저장 버튼을 고정하고 목록만 스크롤한다. 투박한 기본 막대 대신 스크롤할 때만 가는 막대가 나타났다 사라진다.
- 내용·추가·삭제·순서가 달라진 채 닫으면 ‘변경내용을 취소할까요?’를 묻고 실제 취소 버튼은 ‘취소하기’다. ‘계속 편집하기’와 확인창 X·바깥 클릭·Escape는 초안을 유지한다.
- 로딩·조회 오류·빈 목록을 구분한다. 저장 확인 후에만 편집창을 닫고 실패 시 초안·오류를 유지한다. 저장 중 수정·닫기·중복 제출을 막는다.
- 편집 시작 목록을 고정해 원격 변경으로 초안을 덮어쓰지 않는다. 저장 revision 충돌은 안내하며 후속 저장이 조용히 덮어쓰지 못하게 한다.

## 17. 화면 구성과 시각 디자인

- 글꼴 크기·굵기·줄높이, 두 테마의 색상값, 버튼·입력·모달 치수, 여백·반응형·상태별 표현의 상세 기준은 [DESIGN.md](../DESIGN.md)를 따른다. 디자인 변경 시 함께 읽고 갱신한다. 해당 문서의 정비 후보는 확정·구현 완료 규칙과 구분한다.
- 두 역할 모두 좌측 대화·우측 빠른 문구의 공통 화면이다. 별도 수신함이나 처리 대시보드로 나누지 않는다.
- 작은 화면에서도 메시지 입력창을 유지한다. ‘직접 입력’/‘입력창 접기’ 전환은 제거했다.
- 상단 기능의 순서·형태를 유지하며 좁은 방 헤더에서 브랜드 아이콘과 긴 이름을 숨긴다. 홈 브랜드는 자연스럽게 줄바꿈해 남긴다.
- 좌측 제목은 ‘대화 - 방 이름’, 우측은 ‘빠른 문구’와 편집이다. 제목 영역 높이를 맞추고 긴 방 이름은 넘침을 막되 전체 이름 확인 수단을 둔다.
- 기존 Radix 기반 UI·CVA·Lucide SVG와 공통 컴포넌트를 재사용한다. 모든 컴포넌트가 shadcn 패키지에서 왔다고 설명하지 않는다.
- 예배 중 읽기 쉬운 차분한 배치와 기존 중성·녹색 계열 색상을 사용한다. 이모지·장식 위주 디자인·유료 에셋·외부 폰트 의존을 임의 추가하지 않는다. 특정 HEX 색상은 영구 브랜드 합의가 아니다.

## 18. 테마·글자·줄바꿈

- 다크/화이트를 모두 제공한다. 최초 OS 설정을 따르고 이후 사용자 선택을 기기에 저장한다. 저장 접근이 막혀도 사용 자체를 유지한다.
- 대화·문구의 글자 크기를 조절한다. 전체 메뉴와 입력창을 동일 배율로 확대하는 기능은 아니다. 테마와 글자 크기는 현재 계정 동기화 대상이 아니다.
- 큰 글자·긴 문장에서도 문구를 잘라 숨기지 않는다. 짧은 한두 줄은 공통 최소 높이, 긴 문구만 늘리고 필요한 스크롤을 확보한다. 전송 제한 중에는 문구 전체를 흐리게 하지 않는다.
- 한국어 어절 단위 줄바꿈을 기본으로 하고 메뉴·브랜드·주소 등의 의미 단위를 묶는다. 공백 없는 긴 입력은 넘침 방지를 위해 예외 줄바꿈한다.
- 모든 문장을 한 줄로 고정하거나 임의의 고정 줄바꿈만으로 맞추지 않는다. 자동 번역으로 원래 대화 문구가 바뀌지 않도록 한다.

## 19. 모달과 접근성

- X·정상 바깥 클릭·Escape로 닫기를 통일한다. 내부에서 시작한 드래그가 밖에서 끝났다고 닫지 않는다.
- 처리·드래그 중 닫기를 막고 닫은 뒤 열었던 버튼으로 초점을 복귀한다. 미저장 편집은 별도 취소 확인을 거친다.
- 생성자 나가기 창의 ‘방을 유지하고 나가기’와 ‘방을 완전히 닫기’를 나란히 배치한다. 세 번째 ‘계속 대화하기’ 버튼 대신 공통 닫기를 쓴다.
- 완전 종료의 데이터 삭제·참여자 퇴장을 설명하고 파괴적 동작을 구분한다. 권한 없는 종료 선택지는 제공하지 않는다.
- 입력 label·아이콘 버튼 이름·키보드 초점·오류/상태 안내·정렬 위치 안내를 제공한다. 모션 감소 설정을 존중한다.
- 이 구현을 WCAG 전체 준수, 모든 버튼 48px 이상, 200% 확대·VoiceOver·TalkBack 실기기 통과로 확대해 보고하지 않는다.

## 20. 모바일·설치·전체 화면

- 설치는 선택이며 일반 브라우저에서도 이용한다. 설치 안내는 홈 소개 문구 아래에 두고 hover 전에도 버튼 형태를 보인다. 설치된 환경에서는 안내를 숨긴다.
- 제공되는 설치 프롬프트는 사용자가 버튼을 누를 때 실행한다. 없으면 Android Chrome·iPhone Safari 메뉴 안내를 나눠 보여준다.
- 스마트폰 방 화면은 가로 중심이다. 지원 환경에서 방향 잠금을 요청하고 실패하면 회전 안내를 유지한다. 좁은 PC 창·세로 태블릿을 무조건 가리지 않는다.
- manifest와 방 버튼에서 전체 화면을 요청한다. 미지원이면 버튼 위치를 유지하고 비활성화·설명을 제공한다. 모든 기기의 상태바 숨김·자동 회전을 보장하지 않는다.
- 화면 유지 기능은 사용자가 선택한다. 보이는 동안 요청하고 복귀 시 필요하면 재요청하며 퇴장·끄기에서 해제한다. 절전·브라우저 제한에 따른 실패를 안내한다.
- 동적 화면 높이와 노치·홈 제스처 안전 영역을 고려한다. 가상 키보드가 모든 실제 기기에서 가리지 않는다는 검증을 대신하지 않는다.

## 21. PWA 저장·업데이트 범위

- 인터넷 연결이 있어야 대화한다. 서비스 워커는 오프라인 안내 파일만 저장하고 앱 본체·대화·비밀번호·Firebase 응답을 캐시하지 않는다.
- 서비스 워커 설치 실패가 온라인 사용을 막지 않게 한다. 네트워크 실패 시 오프라인 안내와 다시 연결을 제공한다.
- 업데이트로 진행 중 대화 화면을 강제로 새로고침하지 않는다.
- 이름·아이콘·표시 방식이 기존 설치 앱에 즉시 반영된다고 보장하지 않는다. 기기 업데이트·재설치가 필요할 수 있다.
- 설치했다고 푸시·잠금 화면 수신·소리·진동이 구현되는 것은 아니다. 현재 이런 알림 기능은 없다.

## 22. 이름·아이콘·교회 표시

- 화면 이름은 ‘은혜장로교회 예배소통 시스템’, 설치 전체 이름은 ‘예배 소통 시스템’, 짧은 이름과 Apple 홈 제목은 ‘예배소통’이다.
- 승인된 이미지 원본을 파비콘·설치 아이콘·화면 로고에 사용한다. 원본과 생성 기록은 `artifacts/icon-concepts/`에 보존한다.
- `npm run build:icons`는 원본을 크기 변환한다. 현재 출력은 PNG 16/32, ICO 16/32/48, Apple 180, 앱 192/512px다. 임의 새 디자인으로 교체하지 않는다.
- 푸터는 ‘© 현재 연도 은혜장로교회. All rights reserved.’와 ‘경기도 의왕시 부곡시장길 40-1 (삼동 174-1)’을 표시한다. 연도는 자동 갱신한다.
- 푸터는 소유 표시이며 소스 라이선스·이용약관·개인정보 처리방침의 확정을 뜻하지 않는다.

## 24. 서버 보안과 개인정보

- 기본 거절 후 필요한 경로만 허용한다. 승인·역할·소유권·참여 자리·조회 범위·전송 간격을 [서버 규칙](../firebase/database.rules.json)에서 검증한다. 버튼 숨김으로 대체하지 않는다.
- 승인된 이용자의 방 목록 접근과 참여자의 대화 접근을 구분한다. 관리자의 프로필·승인·빈 방 관리 권한이 모든 대화·문구 열람 권한은 아니다.
- 방 비밀번호 원문 대신 무작위 16바이트 salt와 PBKDF2-SHA256 210,000회로 만든 검증값을 사용한다. 이를 종단간 암호화나 관리자도 어떤 검증 정보도 볼 수 없는 구조로 설명하지 않는다.
- 필요한 UID·이메일·역할·승인·문구·방 데이터만 사용한다. 전화번호·생년월일·GPS·음성·영상을 요구하지 않는다.
- 비밀번호·인증 토큰·서비스 계정 비밀 키·실제 사용자 정보·비공개 백업을 코드·Git·테스트 결과물에 넣지 않는다. 방 비밀번호를 URL·로그·복원 힌트에 넣지 않는다.
- Firebase 웹 설정은 앱 식별 정보다. 이를 숨기는 것으로 권한 검증을 대신하지 않는다.
- Hosting에 CSP·프레임 삽입 차단·MIME/참조자·카메라/마이크/위치 권한 제한을 적용한다. 인증 예약 경로와 RTDB long polling을 고려하고 HTML·manifest·서비스 워커 캐시 정책을 유지한다.

## 25. 개발 환경과 코드 형식

- 현재 Node.js는 22.12 이상, 에뮬레이터 Java는 21이다. Windows 실행 정책 문제에는 `npm.cmd`를 사용할 수 있다.
- TypeScript strict·빌드 타입 검사·ES2023·ESNext·`@/*` 경로 별칭을 사용한다. strict를 모든 any 금지 같은 미정 규칙으로 확대하지 않는다.
- Prettier는 작은따옴표·세미콜론 생략·끝 쉼표·줄 길이 100자 기준이다. 별도 ESLint 설정은 현재 없다.
- UTF-8·LF·끝 개행·뒤 공백 제거가 기본이다. Markdown 뒤 공백과 `.bat`/`.cmd` CRLF는 설정의 예외를 따른다.
- `package-lock.json`과 `npm ci`로 재현한다. 직접 의존성에는 범위 지정도 있으므로 모든 선언이 정확한 버전 문자열로 고정된 것은 아니다.
- 보안용 override도 호환성을 확인하고 관리한다. 무조건 최신 주요 버전으로 올리거나 검사 통과를 위해 임의로 낮추지 않는다.
- 기준 파일은 [package.json](../package.json), [tsconfig](../tsconfig.json), [Prettier](../.prettierrc.json), [EditorConfig](../.editorconfig), [Git 줄바꿈](../.gitattributes)이다.

## 26. 개발·시험 데이터 분리

- `npm run dev:local`과 demo Auth/Database 에뮬레이터를 기본으로 개발·검사한다. CLI 로그인·결제 등록 없이 시험할 수 있고 기본 실행 종료 시 로컬 시험 데이터는 남지 않는다.
- 현재 `.env.local`이 있는 PC의 일반 dev·build/preview는 실제 Firebase에 연결될 수 있다. 명령과 대상 프로젝트를 먼저 확인한다.
- 로컬 관리자 지정 도구는 localhost demo 에뮬레이터만 변경한다.
- 운영 확인에는 기존 계정·대화와 무관한 시험 자료를 사용하고 해당 실행 자료만 식별해 정리한다.
- 운영 빌드는 `eh-worship-chat`, 에뮬레이터 false, 필수 웹 설정을 검사한다. 시험 편의를 위해 운영 사용자 권한·데이터를 임의로 바꾸지 않는다.

## 27. 커밋과 스테이징

- 기존 관례는 `종류: 변경 요약`이며 `feat`, `fix`, `docs`, `ci`, `chore`를 사용해 왔다.
- 기존 제목은 영어지만 영어 필수·제목 길이·scope·본문·이슈 번호를 확정하지 않았다. commitlint·활성 Git hook으로 형식을 강제하지 않는다.
- 커밋 전 변경·스테이징을 확인하고 해당 작업 파일만 선별한다. 사용자 스테이징을 임의 해제하거나 통째로 함께 커밋하지 않는다.
- 업로드 파일과 관련 이력에서 비밀을 확인한다. 발견 시 값을 출력하지 않고 해당 업로드를 멈춘다. `.gitignore`는 이미 추적된 파일·과거 이력의 비밀을 지우지 않는다.
- 현재 GitHub 계정명·noreply 작성자 설정을 유지한다. 합의한 기존 공개 이력을 개인정보 정리를 이유로 임의 재작성하지 않는다.
- 기존 origin·브랜치를 보존하고 대상만 업로드한다. 무관한 브랜치·태그 일괄 푸시·강제 푸시·무관한 이력 병합으로 문제를 해결하지 않는다. 변경이 없으면 빈 초기 커밋을 만들지 않는다.

## 28. 브랜치와 PR

- main을 기본으로 임시 작업 브랜치→PR→필수 검사 통과→main으로 반영한다. 별도 장기 develop 브랜치는 합의하지 않았다.
- main 보호는 관리자에게도 적용한다. PR과 최신 main 기준 GitHub Actions의 `verify` 성공이 필요하며 직접 푸시·강제 덮어쓰기·삭제로 우회하지 않는다.
- 다른 사람의 승인 필수 수는 현재 0명이다. CODEOWNERS·마지막 푸시 별도 승인·선형 이력 강제는 현재 설정하지 않았다.
- 최근 squash 병합은 관례이며 GitHub는 merge·squash·rebase를 모두 허용한다. squash만 강제한다고 설명하지 않는다.
- 병합한 원격 브랜치는 자동 삭제하고 로컬은 병합 확인 후 정리한다. 거절·대체한 PR도 닫은 뒤 관련 브랜치를 정리한다.
- PR에 문제·변경 결과·검증·남은 제한을 적는다. 별도 PR·커밋 템플릿과 브랜치 이름 문법은 현재 없다.

## 29. 의존성 업데이트와 저장소 자료

- [Dependabot](../.github/dependabot.yml)의 일반 제안은 npm·GitHub Actions 각각 월 1회, 열린 제안 최대 3개씩이다. 자동 병합하지 않고 검토·검사한다.
- 보안 알림은 일반 업데이트 일정과 별도로 확인한다. 알림 활성화가 취약점 전부 해결을 뜻하지 않는다.
- 임시 제안 브랜치는 정상적인 작업 과정이며 사이트에 자동 배포되지 않는다.
- 환경 파일·로컬 에이전트 설정·편집기 설정·로그·캐시·의존성·빌드·coverage·브라우저 결과·Firebase 로컬 상태·백업·임시 배포 인증 파일을 Git에서 제외한다.
- 값 없는 환경 예제와 승인된 아이콘은 서비스 자산으로 구분한다. 시각 검토 결과는 `artifacts/preview/` 등 Git 제외 위치에 둔다.
- 개인 전역 에이전트 지침을 공개 프로젝트에 복제하지 않는다.

## 30. 자동 검사

- 계산·상태는 단위, 권한·데이터 제약은 Firebase 규칙, 사용자 동작은 Playwright로 검사한다.
- 로컬은 변경 영향에 맞춰 실행하며 GitHub 필수·배포 검사는 모두 통과해야 한다. 문서만 수정하면 내용·링크·차이를 확인하고 앱 전체를 불필요하게 반복 시험하지 않는다.
- [CI](../.github/workflows/ci.yml)는 main push·PR·workflow 재사용 호출에서 실행한다. PR 없는 모든 임시 브랜치 push를 검사하지는 않는다.
- 현재 순서는 `npm ci`→포맷→운영 의존성 보안→단위→타입/빌드→Firebase 규칙→Chromium/WebKit이다. `--omit=dev --audit-level=high`가 개발 도구 전체·모든 심각도 0건 보장을 뜻하지 않는다.
- 실패 원인을 수정하고 필요한 검사를 다시 한다. 검증을 약하게 하거나 무조건 대기 시간을 늘리지 않는다. 재시도 성공만으로 원인 미해결 실패를 덮지 않는다.
- 과거 자동 삭제 후보 한계 실험 3개는 현재 제품 기능 성공 검사가 아니다. 검사 개수는 실행 기록의 시점과 대상을 함께 설명한다.

## 31. 브라우저·시각·실제 기기 검증

- 화면·사용 흐름 변경 시 Playwright 통과와 별도로 브라우저를 조작하고 실제 화면 또는 스크린샷을 열어 본다. DOM 검사·캡처 저장만으로 시각 검토 완료라고 하지 않는다.
- 관련 PC·스마트폰 크기, 다크/화이트·큰 글자에서 줄바꿈·겹침·잘림·모달·스크롤·드래그를 확인한다. 좁은 화면 안내·태블릿은 영향에 따라 확인한다.
- 중요한 반복 오류는 적절한 자동 검사로 보완한다. 기준 이미지 비교를 추가한다면 이미지를 먼저 직접 검토한다. 모든 화면에 비교 검사를 의무 확대하지 않는다.
- PC 모바일 크기·Linux WebKit 검사를 실제 iPhone·Mac Safari 검사로 보고하지 않는다. 회전·화면 유지 모의 API 시험도 실기기 보장이 아니다.
- 키보드·홈 설치·상태바·다른 앱 복귀·화면 잠금은 실제 기기 여부를 구분한다. 모바일 영향이 있는 변경의 핵심만 사용자 확인 대상으로 안내한다.
- 단순 문구 수정마다 전 기능 재시험을 요구하지 않는다. 이 기준 때문에 별도 모바일 에뮬레이터·도구를 무리하게 설치하지 않는다.
- 실행 검사·직접 본 화면·실패/미실행 이유·남은 실기기 확인을 나눠 보고한다. 검사 개수만으로 품질을 보장하지 않는다.

## 32. Actions 실행과 배포 인증

- 현재 CI는 Ubuntu 24.04·Node 22·Temurin Java 21, GitHub Actions 커밋 SHA 고정, 기본 읽기 권한과 checkout 인증 미보존을 사용한다.
- Playwright는 1 worker·순차 실행과 로컬 demo 에뮬레이터를 사용한다. 실패 trace·화면 자료는 3일 보관한다. 일반 verify 제한 시간은 20분이며 새 CI로 이전 실행을 취소할 수 있다.
- 배포는 승인받은 전용 계정과 WIF 단기 인증을 사용한다. 장기 서비스 계정 비밀 키 파일을 추가하지 않는다.
- 구성된 인증 연결은 저장소·소유자 ID, main, 지정 deploy workflow, 수동 실행으로 제한한다. 현재 외부 IAM 상태를 보고할 때는 실제 재조회 여부를 구분한다.
- 전용 계정에는 승인받은 Hosting·RTDB 관리, 프로젝트 조회·API 사용 권한이 있다. 읽기 전용으로 설명하지 않는다.

## 33. 배포 순서

- 로컬 수정·커밋·푸시·main 병합·실제 배포를 구분한다. 커밋·병합만으로 사이트를 바꾸지 않는다.
- 배포 전 변경·자동 검사·시각 확인·남은 실기기 확인을 짧게 안내한다. 중요한 권한·사용 흐름의 알려진 오류는 먼저 알리고 해결한다.
- 사용자가 배포를 요청하면 진행하며 같은 변경의 배포 승인을 반복해 묻지 않는다.
- 현재 경로는 main의 [Deploy verified version](../.github/workflows/deploy.yml)에서 `deploy` 확인값으로 수동 실행하는 방식이다. 공통 검사 재실행 성공 후 운영 빌드와 Database·Hosting 배포를 한다.
- production 배포 그룹은 진행 중 배포를 새 실행이 취소하지 않으며 배포 job 제한 시간은 10분이다. 검사·인증 조건을 우회하지 않는다.
- 예배 중 서비스 사용에 영향을 주지 않는 때 진행한다. workflow 성공만으로 끝내지 않고 실제 HTTPS 주소에서 변경과 관련 주요 동작을 확인한다. 못 한 항목은 완료로 표시하지 않는다.

## 34. 백업·복구·롤백

- 권한 규칙·데이터 구조 등 운영 영향이 큰 변경은 [최신 복구 안내](firebase-setup.md)를 읽고 필요한 백업과 호환성을 확인한다.
- `npm run backup:settings`는 profiles·access·administrators·presets를 비공개 `.backups/시간/`에 저장한다. 이메일·문구가 있으므로 공개하지 않는다.
- 방·대화·방 비밀번호 검증값·Authentication 비밀번호·CLI 토큰은 포함하지 않는다. 순차 조회이며 원자적 스냅숏이 아니다. manifest가 없으면 완료 백업으로 보지 않는다.
- 복구 전에 현재 상태도 백업하고 실제 Auth UID 존재와 현재 권한 의도를 확인해 필요한 설정만 비교 복원한다. 루트 전체 덮어쓰기·Auth 계정 자동 재생성을 하지 않는다.
- 삭제한 방 대화는 이 설정 백업으로 복구할 수 없다. 백업 파일 존재만으로 복구 검증이 끝났다고 하지 않는다.
- Hosting 롤백과 Database 규칙 복구는 별개다. 이전 앱·현재 규칙·데이터의 호환성을 확인하고 규칙 수정은 에뮬레이터 검사 후 별도 배포한다. 복구 편의를 위해 인증·승인 제한을 풀지 않는다.

| 관리자 승인 화면 직행·역할 고정               | 기본 홈·입장별 역할 선택          |
| 임시 아이콘·긴 홈 아이콘 이름                 | 승인 이미지·짧은 이름 ‘예배소통’  |
| 자체 서버·Socket.IO·PostgreSQL·Outbox         | 현재 Firebase 구성                |

자동 삭제 후보를 시험한 결과는 해당 후보의 한계다. Firebase에서 가능한 모든 설계에 대한 불가능 증명으로 확대하지 않는다. 과거 문서의 ‘확정 요구’ 표기도 후속 결정으로 대체됐을 수 있다.

## 36. 과거 검토했지만 도입하지 않은 사항

- Web Push·OS 알림·소리/진동·잠금 화면 응답·배지·자동 재촉·긴급 알림.
- 요청 상세·취소/완료 경합·처리 불가 사유·스레드·만족 회신·담당자 인계와 처리 이력.
- 공통 문구 배포·다수 수신자·통계·파일 전송·외부 서비스/장비 연동.
- 별도 알림 서버·영구 오프라인 전송함·IndexedDB 복구·작업 폐기 토큰·기기/세션 목록·원격 종료·공용 Mac 자동 잠금.
- 교회 실제 기기·네트워크·전원·화면 잠금 조사, 리허설·제한 도입, 영상 송출/화면 캡처에 사적인 대화나 알림이 노출되지 않는지 확인.
- 모호한 요청의 대상 정리, 장애·무응답 시 현장 연락 수단·대체 담당자·전환 기준·복구 담당자 마련.
- 전달 지연·조작 횟수·주의 분산·중복/오발송·복구 시간을 측정하는 운영 평가.

마지막 세 항목은 [과거 운영 검토](planning/04-operations-and-validation.md)의 제안이다. 실제 담당자·전환 시간·리허설 횟수·합격 수치를 확정하거나 현장에서 검증했다고 말하지 않는다. 다른 과거 기능도 새 개발 지시로 되살리지 않는다.

## 37. 미정·미구현 사항

- 계정 탈퇴, 거절·미사용·옛 익명 계정 정리 주기, 프로필·승인·문구 보존 기간.
- 일반 계정 역할 변경, 방 소유권 양도, 생성 뒤 이름·비밀번호 변경 화면.
- 관리자 추가·위임 화면, 모든 기기 강제 로그아웃.
- 방 비밀번호 온라인 시도 제한, App Check·CAPTCHA·추가 관리자 인증, 프로젝트 전체 남용 방지. 현재 제한을 이런 보호가 모두 있는 것으로 설명하지 않는다.
- 정기 백업 주기·보관 기간·외부 보관·암호화 정책·복구 훈련·장애 복구 목표와 대체 운영자.
- 실제 지원 기기·OS 최소 버전, 최대 수용 성능·전송 지연 합격 수치, 검사 커버리지 최소 비율.
- 모든 화면 기준 이미지 비교·axe 접근성 감사·Firefox 필수 검사. 현재 font·레이아웃 검사만으로 과거 대비·200% 확대 목표를 모두 충족했다고 하지 않는다.
- 커밋 언어·본문·제목 길이·scope·이슈 번호·한 커밋 크기, 브랜치 이름 강제, commitlint/hook, squash만 허용.
- 버전 증분·정기 릴리스·태그·CHANGELOG 의무. 정리 시점 package 버전은 `0.1.0`, `private: true`이며 Git 태그·GitHub Release는 없었다. 저장소 공개 여부와 package private는 별개다.
- 소스 라이선스, 이용약관·개인정보 처리방침. LICENSE와 package license는 현재 없으며 MIT 등을 선택했다고 하지 않는다.
- 별도 staging·PR 미리보기 배포·정기 배포 시간·장애 응답시간 보장.

미정은 필수 개발 목록이 아니다. 필요할 때 새 합의와 영향 확인을 거친다.

## 38. 문서·답변·완료 보고

- 대화 방식은 실행 환경이 연결하는 전역 AGENTS 관리 원본에 위임한다. 개인 경로·전역 원문을 프로젝트에 복제하지 않는다. 전역 변경 요청에는 그 원본의 백업·수정·연결 확인 절차를 따른다.
- 프로젝트 원칙은 AGENTS, 상세 결정은 이 문서, 상세 디자인 수치·상호작용은 DESIGN, 이용·실행 안내는 README, 운영·복구 절차는 Firebase 안내, 과거 경위는 개발·기획 기록으로 구분한다.
- 사실·제안·현재 구현·확인 못 한 내용을 구분하고 최신 결정에 맞춰 설명한다. 구현값·관례·과거 실험을 사용자 확정 규칙이나 현재 검증 성공으로 바꾸지 않는다.
- 로컬 반영·커밋·푸시·PR 병합·배포를 구분한다. 실행한 검사와 실제 본 화면·실기기 확인도 구분한다.
- 서브에이전트를 요청받아 검토할 때 사용 수와 해당 검토 차수를 알린다. 이를 매 작업마다 4개를 의무 실행하는 규칙으로 확대하지 않는다.
- 공통 초기 설정은 초기화 요청에만 적용한다. 문서 수정으로 기존 저장소 재생성·공개 범위 변경·초기 커밋을 실행하지 않는다. Codex/Windows 환경 진단 규칙은 앱 제품 요구사항과 구분한다.
