# 첫 구현과 검증 기록

2026-10-08. 이전 1~9차 검토 중 최신 사용자 결정에 맞춘 첫 구현이다. 실제 Firebase 구성과 [Hosting 공개 배포](https://eh-worship-chat.web.app)를 완료했으며 실제 휴대폰·Mac 현장 검증은 남아 있다.

## 구현 경계

React·TypeScript·Vite, Lucide SVG 아이콘, Radix Slot/CVA 기반 버튼과 입력 컴포넌트를 사용한다. 종속성 버전은 package-lock.json으로 고정한다. 별도 인물 계정·읽음 확인·처리 상태·예배 회차·담당자 관리는 구현하지 않는다. 준비된 문구도 일반 채팅 메시지이며 상태 변경 명령이 아니다. 첫 버전 이후 사용자 요청으로 방 안에서 문구를 추가·수정·삭제·정렬하는 편집기를 추가했다.

방송실과 인도자 화면은 같은 좌우 배치를 사용한다. 터치 기기의 인도자 세로 화면에서는 회전 안내를 보여 준다. 브라우저 자체의 강제 회전 잠금을 보장하지는 않는다. 좁은 PC 창에는 회전 안내가 나타나지 않는다. 글자 16~24px·기본 18px·2px 간격은 현재 테스트 가능한 초기 값이며 사용 기기에서 조절할 수 있다.

다크/화이트 모드를 모두 제공한다는 사용자 답변을 반영했다. 처음에는 운영체제 설정을 따르고 화면 버튼으로 변경한 값을 가능할 때 기기에 저장한다. 방 코드 6자리, 메시지 500자, 비밀번호 1~128자는 현재 구현의 제한이다. 비밀번호는 공백까지 그대로 비교하고 코드 선행 0은 유지한다.

## 확정한 Firebase 구성과 바뀐 방 종료 정책

사용자가 Firebase만 사용하고 어려운 기능은 조정하기로 선택했다. React 앱이 Firebase Authentication과 Realtime Database에 직접 연결한다. Cloud Functions·Cloud Run·Mac 상시 서버를 사용하지 않는다. 초기 화면 검증용 WebSocket 서버는 제거했다. Firebase 에뮬레이터 검증 후 실제 프로젝트·웹 앱·싱가포르 데이터베이스를 생성하고 익명 인증을 설정하고 보안 규칙을 배포했다. 이후 사용자 요청으로 Hosting 공개 배포를 진행하고 배포 주소에서도 실제 통신 검증을 통과했다.

사용자 답변으로 확정한 사항은 다음과 같다.

1. Firebase만 사용하고 무료 범위에서 기능을 조정한다.
2. 다크/화이트 모드를 사용자 버튼으로 전환한다.
3. 방송실의 나가기에서 ‘방을 유지하고 나가기’와 ‘방을 완전히 닫기’를 고른다. 네트워크 문제 등으로 나가진 경우에는 방을 유지한다.

따라서 마지막 참여자 단절도 방 전체 삭제를 발생시키지 않는다. 방 닫기를 선택할 때만 방과 대화를 삭제한다. 이전 자동 삭제 조건을 유지하는 구현이 아니다. 사용자 답변에 따라 비밀번호로 재입장한 방송실도 전체 종료할 수 있다. 실제 프로젝트 ID는 `eh-worship-chat`이다. 한글 관리용 이름이 Google에서 거절되어 사용자 확인 후 ‘EH Worship Chat’으로 생성했으며 서비스 화면 이름은 후속 요청에 따라 ‘은혜장로교회 예배소통 시스템’으로 변경했다. 데이터베이스 위치는 사용자 선택에 따라 싱가포르다. CLI 로그인 완료와 결제 계정 미연결(`billingEnabled: false`)을 확인했다.

Firebase 에뮬레이터에서 세 가지 실험을 통과했다. 여기서 통과는 후보 방식의 한계를 재현했다는 의미다.

| 실험 | 관찰 결과 |
| --- | --- |
| 두 명이 있는데 마지막 한 명만 허용되는 방 전체 삭제를 onDisconnect에 예약 | 예약 시 보안 규칙에서 거절됨 |
| 각자 자기 접속 표시만 onDisconnect로 삭제 | 접속 표시는 모두 사라져도 메시지와 비밀번호 검증 정보는 남음 |
| 혼자일 때 전체 삭제 예약 후 다른 참여자가 입장 | 실제 연결 종료 시 규칙을 다시 검사하여 전체 삭제가 거절됨 |

이는 시험한 세 방식이 이전 자동 삭제 조건을 충족하지 못한다는 근거다. Spark의 모든 설계가 불가능하다고 입증한 것은 아니다. 이 실험은 `last-disconnect.test.ts`에 남기고, 변경된 유지·명시적 종료 방식은 `firebase/database.rules.json`과 `room-security.test.ts`에서 별도로 구현·검증한다. 접근 기본값은 거절하며 입장 검증을 통과한 요청만 허용한다.

[Firebase onDisconnect 공식 설명](https://firebase.google.com/docs/database/web/offline-capabilities)에 등록·실행 시 규칙 검사 동작이 설명되어 있다. [Cloud Functions 시작 문서](https://firebase.google.com/docs/functions/get-started)는 배포에 Blaze 요금제가 필요함을 명시한다. 유료 전환·결제 등록을 하지 않았으며, 무료 한도에서 영구 무중단 운영을 보장하지 않는다. 다른 서버로 전환하지 않는다.

## 방과 메시지 처리

- 비밀번호는 무작위 salt와 PBKDF2-SHA256으로 검증값을 만든다. 원문 비밀번호는 서버·URL·로그에 저장하지 않는다. 목록의 코드·생성 시간·방 ID·salt는 로그인한 사용자가 읽을 수 있지만 검증값·대화는 입장한 참여자만 읽는다. 검증값을 이용한 입장 허용은 Firebase 보안 규칙이 검사한다.
- 2026-10-09부터 이메일·비밀번호로 가입하고 같은 계정으로 로그인한다. 방 삭제와 계정 삭제는 별개다. 기존 익명 레코드는 자동 정리하지 않으며 새 익명 가입은 껐다. 운영상 두 공용 계정을 쓰는 방식이고 계정 수를 강제로 두 개로 제한하지 않는다.
- 접속 표시는 연결별로 관리하고 onDisconnect로 자기 표시만 제거한다. 단절 인지에는 Firebase의 연결 감지 지연이 있다. 방·대화는 남기며 방송실의 명시적 전체 닫기에서 방과 목록을 원자적으로 삭제한다. 일부 경로만 지우는 요청도 규칙으로 거절한다.
- 아무도 남아 있지 않아도 다시 비밀번호로 입장하면 남겨 둔 방의 기록을 받는다. 새로고침에서는 유효한 Firebase 인증과 탭의 방 식별 정보가 있으면 자동 복원한다.
- 방 ID·코드·계정 UID를 sessionStorage의 v2 키에 저장하고 방 비밀번호는 저장하지 않는다. Firebase 인증은 browserLocalPersistence로 유지하며 저장 차단 시 메모리에서만 유지한다. 명시적 나가기·방 종료는 방 키만 제거하고 로그아웃은 인증과 현재 탭의 방 상태를 함께 정리한다. 계정이 바뀌면 이전 계정의 방을 자동 복원하지 않는다. 글자·모드·문구 설정은 별개이며 전체 저장소를 지우지 않는다.
- 연결 종료·방 변경·글자 크기 변경은 서로 분리한다. blur·visibility 변경만으로 나가기 처리를 하지 않는다.
- 확정된 메시지는 서버 시각과 메시지 ID의 공통 순서로 표시한다. 물리적인 버튼 누름 시간순을 보장하는 별도 순번 서버는 없다. 일반 문구 반복은 새 ID이며 동일 전송의 재시도는 같은 ID다. 서버 접수와 사람의 확인을 혼동하는 읽음 표시는 없다.
- 방·메시지 쓰기는 REST 요청으로 처리하여 Firebase SDK의 오프라인 쓰기 큐에 넣지 않는다. 실시간 수신과 접속 표시 정리는 SDK를 사용한다. CREATE는 응답이 불명확해도 자동 반복하지 않으며 같은 방을 조회해 확인한다. 닫힌 방의 늦은 메시지·입장 쓰기는 규칙에서 거절한다.
- 방송실·인도자는 개인 신원 확인이 아닌 사용 역할이다. 로그인하고 같은 방 비밀번호를 아는 사람이 방송실로 입장할 수 있는 교회 내부 신뢰 모델이다. 강한 관리자 개인 인증이나 온라인 비밀번호 시도 횟수 제한은 이번 구현에 없다.

## 검증 및 남은 확인

첫 버전 확인 결과: 빌드·타입 검사 통과, 설정 단위 테스트 2개, 운영 규칙 테스트 7개, 이전 자동 삭제 후보 실험 3개, Chromium 화면 테스트 7개 통과. Firebase 규칙은 실제 서비스 계정 대신 demo 에뮬레이터에서 확인한 결과다. 후속 개선 검증은 아래에 별도로 기록한다.

추가로 실제 `eh-worship-chat`을 연결한 운영 빌드를 Windows Chromium에서 검증했다. 방 생성, 비밀번호 오류·정상 입장, 양방향 문구·일반 메시지, 새로고침과 방 유지 후 재입장 기록, 새 방송실 인증 세션의 전체 방 닫기를 확인했다. Realtime Database 조회로 방과 목록 삭제까지 확인했고, 이 검증에서 만든 익명 계정 3개를 정리했다. 실제 휴대폰이나 Mac을 사용한 검증은 아니다.

Hosting 배포 후 `https://eh-worship-chat.web.app`에서 위 주요 통신 동작을 다시 확인했다. PC 크기와 휴대폰 가로 크기의 Chromium 화면으로 검증했으며 시험 방과 해당 실행의 임시 익명 계정 3개는 제거했다. 운영 빌드·타입 검사도 다시 통과했고 에뮬레이터 연결이 꺼진 운영 설정을 확인했다.

`npm run build`, `npm test`, Chromium 브라우저 테스트, Firebase 에뮬레이터 실험을 실행한다. 두 개의 독립 브라우저 문맥으로 입장 비밀번호, 양방향 일반 메시지, 반복 문구, 미작성 문장 보존, 글자 크기와 버튼 높이, 재입장 기록, 방 닫기와 마지막 소켓 종료를 확인한다. 추가로 한글 조합 Enter·키 반복·저장소 차단·좁은 PC 창·가로/세로 전환·스크롤 위치와 입력 포커스를 검증한다.

Windows 환경의 WebKit은 `brotlicommon.dll`, `ssl-60.dll`, `libwebpmux.dll` 실행 구성요소가 부족하여 브라우저를 실행하지 못했다. Safari 통과로 기록하지 않는다. 실제 목사님 휴대폰과 교회 Mac에서 화면 잠금·앱 전환·한글 키보드·네트워크 전환 검증이 남아 있다.

`npm audit --omit=dev`에서는 운영 앱 의존성 취약점이 0건이었다. Firebase의 grpc 간접 의존성에 호환 수정 버전 override를 적용했다. 전체 검사에는 Firebase CLI 개발 도구의 간접 의존성 경고 11건(높음 7, 보통 4)이 남았다. 호환 범위의 `npm audit fix`로 해결되지 않았으며 무리한 구버전 다운그레이드는 적용하지 않았다. 개발 도구 의존성 경고와 입장 시도·자원 남용 방어는 남은 보완 사항이다. 공개 배포가 이 제한을 해소한 것은 아니다.

다음 작업은 실제 휴대폰·교회 Mac에서 접속과 예배 중 사용 흐름을 확인하는 것이다. React Native와 앱스토어 배포는 이번 구현에 포함되지 않는다.

## 휴대폰 테스트 후 개선 — 2026-10-08

사용자가 로그인 없이 역할당 1명 입장, 우선 설치형 웹앱으로 개선, 문구를 기기마다 역할별 저장하도록 선택했다. 기존 React 웹을 WebView로 감싸는 React Native 앱도 가능하지만 이번에는 PWA를 사용한다.

- 역할별 `seats`가 하나의 사용자·연결 ID를 가리킨다. 기존 연결이 살아 있으면 다른 연결의 점유를 서버 규칙에서 거절한다. 활성 연결 생성·역할 점유·입장 알림은 한 번의 원자적 쓰기로 처리한다. 회원가입을 추가하거나 먼저 접속한 사람을 강제로 내보내지 않는다.
- 연결마다 onDisconnect로 해당 연결 제거와 단절 알림을 예약한다. 역할 자리는 연결의 실존 여부로 판단하므로 참조가 남아 있어도 새 접속이 점유할 수 있다. 규칙은 현재 역할 점유자만 메시지를 보내거나 방송실 방 닫기를 할 수 있게 한다. 연결이 끊긴 것을 서버에서 감지하기 전까지는 재입장이 잠시 제한될 수 있다.
- 입장·명시적 퇴장·연결 끊김 알림을 서버 시각으로 대화와 함께 정렬한다. 종료 예약만 실행되고 실제 입장은 완료되지 않은 시도는 알림에서 제외한다. 단절 기록이 생긴 연결 ID의 늦은 입장 쓰기도 차단한다. 방을 닫으면 이 기록도 삭제한다.
- 빠른 문구 편집기는 방 안에 있다. 추가·수정·삭제·위아래 정렬 후 저장하며, 취소하면 원래 목록을 유지한다. 역할별 30개·내용 120자·분류 16자를 허용한다. localStorage 쓰기가 거절되면 저장 완료로 표시하지 않는다.
- 작은 터치 화면에서는 브랜드와 별도 방 닫기 단축 버튼을 줄이고 상단 높이를 48px로 맞췄다. 방 닫기는 ‘나가기’ 선택지에 남아 있다. 방송실도 입력창을 접어둘 수 있고, 최대 글자 크기에서도 문구가 잘리지 않도록 높이를 늘려 스크롤한다.
- 설치 manifest·Lucide 기반 아이콘·설치 안내를 추가했다. 서비스 워커는 오프라인 안내 파일만 저장하며 웹 앱 본체·대화·인증 정보·Firebase 응답을 캐시하지 않는다. 실행 중 화면을 강제로 새로고침하지 않는다.

설정·문구 단위 테스트 4개, 운영 보안 규칙 테스트 12개, Chromium 화면 테스트 10개를 통과했다. Chrome 설치 조건 오류 없음, manifest·192/512px 아이콘·설치 안내·오프라인 대체 화면·온라인 복귀를 로컬 운영 빌드에서 확인했다. 실제 Android 홈 화면 설치와 iPhone·Mac Safari 현장 확인은 남아 있다.

후속 변경은 같은 날 기존 Firebase Hosting 주소와 실제 데이터베이스 규칙에 배포했다. 공개 주소에서도 중복 방송실 차단·문구 수정의 기기 저장·퇴장 알림·양방향 메시지·재입장·전체 삭제 검증을 통과했다. 테스트 방과 해당 실행에서 만든 익명 계정 4개를 정리했다. 유료 서비스나 요금제 변경은 추가하지 않았다.

## 문구 편집·표시 개선 — 2026-10-08

- 문구 분류를 제거했다. 저장 키를 유지하고 기존 저장 데이터에서 문구와 순서만 읽으므로 이전에 편집한 내용은 보존한다. 문구 제한은 역할별 30개·120자다.
- dnd-kit의 손잡이 드래그와 키보드 정렬을 추가했다. 입력 칸을 선택하거나 스크롤할 때는 드래그가 시작되지 않는다. 기존 위아래 버튼도 유지하며 이동한 카드에 한 번의 부드러운 테두리 펄스를 표시한다. 모션 감소 설정에서는 정적인 테두리로 대체한다.
- Radix Scroll Area를 적용해 기본 스크롤바를 숨기고 스크롤 중에만 가는 막대를 표시한다. 편집창의 제목과 저장·취소 버튼은 고정하고 목록만 스크롤한다. 작은 가로 화면에서는 카드의 이동·삭제 버튼을 한 줄로 모았다.
- 설명은 한국어 어절 단위로 줄바꿈하고, 긴 공백 없는 입력에만 비상 줄바꿈을 허용한다. 설치 안내는 Android·iPhone 단계별로 나누고 메뉴 이름을 한 줄로 유지한다.
- 홈 이름과 문서 제목은 ‘은혜장로교회 예배소통 시스템’, 설치 이름은 ‘예배 소통 시스템’으로 변경했다. manifest의 동일한 앱 ID·경로를 유지한다.
- manifest의 표시 방식을 fullscreen으로 바꾸고 지원 환경에 전체 화면 버튼을 제공한다. iPhone 등 일부 환경에서 OS 상태바 숨김은 보장하지 않는다. 실제 휴대폰 상태바 동작은 현장 확인 대상으로 남긴다. [표시 방식과 대체 동작](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/display)
- 이미지 생성으로 [아이콘 후보](../artifacts/icon-concepts/worship-communication-v1.png)를 만들었으나 사용자 검토 전이므로 앱·파비콘에는 적용하지 않았다.

단위 테스트 5개와 Chromium 화면 테스트 13개, 타입 검사·운영 빌드를 통과했다. 화면 테스트는 마우스 및 키보드 정렬·취소·저장 복원, 스크롤바 표시·숨김, 고정된 저장 버튼, 320px 설치 안내의 메뉴 줄바꿈, 전체 화면 진입·종료를 포함한다. 실제 iPhone·Mac Safari 통과를 의미하지 않는다.

익명 계정 누적에 관한 질문에는 세션 인증이 새 계정을 생성할 수 있고 방 삭제와 Authentication 계정 삭제는 별개임을 설명했다. 고정 계정 로그인으로의 전환을 논의 중이며, 현재 인증 코드·계정·인증 설정은 이 화면 개선에서 변경하지 않았다.

설치형 웹앱의 manifest·아이콘 크기·Chrome 설치 가능 조건·오프라인 안내와 복귀도 로컬 운영 빌드에서 통과했다. 이후 Hosting만 배포하고 공개 주소의 파일 9개가 로컬 운영 빌드와 일치함을 해시로 확인했다. 실제 Firebase에서도 비밀번호 검증·중복 역할 차단·양방향 대화·문구 편집 유지·방 유지 후 재입장·방 종료를 확인했다. 검증용 방과 이 실행에서 만든 익명 계정 4개만 정리했다. 기존 계정·방·데이터베이스 규칙·요금제는 변경하지 않았다.

## 승인된 아이콘과 홈 화면 이름 적용 — 2026-10-08

사용자가 이미지 시안을 승인하여 원본 디자인을 그대로 파비콘·설치 아이콘·화면 로고에 적용했다. `scripts/build-icons.mjs`는 기존 PNG를 Chromium Canvas로 크기만 변환하며 새 이미지를 생성하지 않는다. 16/32px PNG, 16/32/48px을 포함하는 ICO, Apple용 180px PNG, 앱용 192/512px PNG를 `public`에 저장한다. 원본 이미지와 최초 생성 프롬프트는 `artifacts/icon-concepts`에 보존한다.

아이콘 참조에 버전을 붙여 기존 캐시와 구분하고, 사용하지 않는 이전 SVG 아이콘을 제거했다. 사용자 선택에 따라 manifest의 `short_name`과 Apple 홈 화면 제목을 ‘예배소통’으로 줄였고 설치 안내에도 반영했다. 전체 서비스 제목·manifest의 앱 ID·시작 URL은 유지했다. 기존 설치 앱의 이름·아이콘 반영 시점은 브라우저와 운영체제에 따라 다르다. [설치 앱 업데이트 안내](https://web.dev/learn/pwa/update)

빌드·타입 검사·포맷 검사를 통과했다. ICO의 세 이미지 항목과 모든 연결된 PNG의 실제 크기·브라우저 디코딩, 짧은 이름과 화면 로고, Chrome 설치 가능 조건, 오프라인 안내와 복귀를 확인했다. 원본의 밝은 심벌은 마스크 안전 영역 안에 있음을 검사하고 로컬 원형·사각형·파비콘 미리보기(`artifacts/preview/approved-icons.png`)를 눈으로 확인했다. 검증 스크린샷은 Git에 포함하지 않는다. 실제 휴대폰의 기존 설치 아이콘 업데이트 완료 여부는 별도 현장 확인이 필요하다.

Hosting 배포 후 파일 12개의 해시가 로컬 빌드와 일치함을 확인했다. 실제 주소에서도 짧은 이름과 버전이 붙은 아이콘 URL·파비콘 응답을 검증했다. 인증 설정과 데이터베이스는 이번 아이콘 배포에서 변경하지 않았다.

## 이메일 로그인 구현 — 2026-10-09

- 홈 카드에서 로그인·회원가입·비밀번호 재설정 컴포넌트를 전환한다. 이메일은 유지하고 비밀번호·오류는 전환 시 초기화한다. 가입 시 8~128자 비밀번호와 확인란을 검사하고 중복 제출을 막는다. Firebase가 계정·비밀번호를 관리한다.
- 로그인 후 기존 역할 선택을 사용한다. 나가기는 로그인을 유지하고 로그아웃은 별도 버튼이다. 같은 브라우저의 탭끼리는 인증을 공유하며 기기별 로그인은 독립적이다. 방별 역할은 여전히 연결 ID를 기준으로 한 자리만 허용한다.
- Firebase 초기화 시 영구 저장 방식을 선택해 탭 간 인증 변경을 수신한다. 계정 전환 시 구독·임시 메시지·방 복원 정보를 지운다. 다른 탭에서 인증이 바뀌어 onDisconnect 권한을 잃는 경우를 대비해 기존 인증으로 자기 연결만 정리한다. 다른 접속의 자리를 제거하지 않는다.
- 비밀번호 재설정 메일은 한국어를 요청한다. 등록 여부와 관계없이 동일한 안내를 보여 준다. 실제 메일 수신까지 보장하는 검증은 아니며 에뮬레이터에서 발급 코드로 비밀번호 변경과 재로그인까지 확인했다.
- 로그인 전에는 Realtime Database 연결을 열지 않으며 방문·새로고침으로 계정을 생성하지 않는다. 이메일 제공자 활성화와 익명 제공자 비활성화만 수행하고 기존 계정은 삭제하지 않았다. 이전 익명 앱의 퇴장 예약이 유지되도록 기존 참여자의 방 읽기·자기 연결 정리를 호환 허용한다. 새 데이터 쓰기는 이메일 계정으로 제한한다.

타입 검사·운영 빌드, 단위 시험 5개, Firebase 규칙 13개와 이전 방 삭제 방식 실험 3개, Chromium 화면 시험 19개를 통과했다. 화면 시험에는 로그인 유지, 비밀번호 오류·중복 가입, 익명 상태 전환, 탭 간 로그아웃·계정 변경, 같은 계정의 중복 역할 차단과 자리 재사용, 비밀번호 재설정, 저장 차단, 320px·짧은 가로 화면을 포함한다. 실제 iPhone·Mac Safari 검증은 남아 있다.

실제 Hosting 반영 후 파일 12개의 해시가 운영 빌드와 일치했다. 공개 주소에서 회원가입·로그아웃·재로그인, 같은 브라우저의 다른 탭 로그아웃 후 자리 해제와 재입장, 중복 역할 차단, 방 비밀번호 검증, 양방향 대화, 문구 편집 유지, 재입장과 방 닫기를 확인했다. 배포 전·후 검증마다 생성한 테스트 계정 4개와 해당 테스트 방만 정리했다. 결제 계정 미연결(`billingEnabled: false`)과 이메일 제공자 활성화·익명 제공자 비활성화를 다시 확인했다.

## 계정 역할·방 소유권·화면 수정 — 2026-10-09

사용자의 배포 요청에 따라 검증을 마친 변경을 Firebase Hosting과 Realtime Database 보안 규칙에 배포했다. 사용자 답변을 기다리는 항목은 모달 닫기 방식, 내부 이용 제한 방식이다.

- 회원가입에서 방송실·예배인도자 역할을 선택하고 profiles/{uid}에 한 번만 기록한다. 역할은 이후 로그인·재접속에도 유지하며 사용자가 서버에 직접 요청해 바꾸거나 타인의 역할을 읽고 수정할 수 없다. 기존 이메일 계정은 다음 접속에서 역할을 한 번 설정한다. 인도자 계정은 방 생성이나 방송실 역할의 입장을 할 수 없다.
- 방 닫기는 저장된 meta.owner와 현재 계정 UID가 같고 방송실 자리도 점유한 경우에만 허용한다. 다른 방송실 계정은 빈 방송실 자리에 들어와 대화할 수 있지만 방 닫기는 할 수 없다. UI 버튼과 실제 삭제 요청을 함께 제한했다.
- 방 생성 화면에서 기본 이름 ‘대화방 6자리 숫자’를 미리 입력하고 사용자가 1~40자로 바꿀 수 있게 했다. 방 목록과 입장 후 제목은 저장된 이름을 사용하며 내부 식별 코드와 분리했다. 이전 이름 없는 방은 기존 코드에서 제목을 만든다.
- 모든 크기의 메시지 입력창을 항상 표시한다. 상단 버튼의 순서·크기·표시는 공통으로 사용하고 좁은 화면에서는 브랜드만 숨긴다. 전체 화면 API 미지원·설치 앱 모드에서도 버튼 위치를 유지하고 실행 불가능한 동작은 비활성화해 설명한다. 대화와 빠른 문구 제목은 같은 52px 높이를 사용한다.
- 설치 manifest에 landscape 방향을 요청하고 지원하는 휴대폰의 방 진입·전체 화면 진입에서 화면 방향 잠금을 요청한다. OS·브라우저가 거절하는 경우에는 회전 안내를 유지한다. 세로 태블릿은 안내로 가리지 않는다. API 호출 여부를 시험했으며 실제 기기의 강제 회전 성공을 검증한 것은 아니다.
- 푸터는 ‘© 현재 연도 은혜장로교회. All rights reserved.’로 바꾸었다. 사용자가 알려 준 주소 ‘경기도 의왕시 부곡시장길 40-1 (삼동 174-1)’를 그 아래에 추가하고, 좁은 화면에서도 도로명과 건물 번호·괄호 속 지번이 각각 함께 줄바꿈되게 했다.

단위 시험 5개, 서버 규칙 시험 16개와 과거 자동 삭제 후보 시험 3개, Chromium 화면 시험 24개에 해당하는 검증을 통과했다. 기존 화면 시험 19개 전체와 추가 시험 5개를 실행했고, 후속 화면 변경의 영향 범위도 다시 확인했다. 화면 크기별 버튼 치수·제목 위치 일치와 방 이름 유지·생성자 삭제 제한을 포함한다. 운영 데이터는 읽기만 했으며 확인 시점에 남아 있는 방은 0개였다.

이 배포 시점에는 모달의 X·바깥 클릭 통일은 제안만 한 상태였다. 후속 모달 적용은 아래에 기록한다. 내부 이용 제한은 역할별 초대코드를 추천했으나 아직 선택되지 않았으며, 역할만 고정하고 가입 제한을 추가하지 않았다. 무료 구성에서 초대코드로 방과 대화 접근을 막는 것과 Firebase Authentication 계정 생성 요청 자체를 사전 심사하는 것은 다른 범위다.

## 모달 닫기와 편집 보호 — 2026-10-09

사용자가 선택한 X 버튼·바깥 클릭 닫기를 설치 안내, 방 나가기·닫기, 문구 편집창에 공통 적용했다. Escape도 같은 동작을 사용한다. 창 내부에서 누른 뒤 바깥으로 끌어 놓는 동작은 닫기로 처리하지 않으며, 처리 중인 방 종료 요청이나 문구 드래그 중에는 닫기를 막는다. 창을 닫으면 열었던 버튼으로 키보드 초점을 돌린다.

방 생성자의 나가기 창에는 ‘방을 유지하고 나가기’와 ‘방을 완전히 닫기’ 두 버튼만 나란히 둔다. 문구 편집의 내용·추가·삭제·순서 변경을 저장하지 않고 닫으려 하면 버리기 확인창을 표시한다. 확인창을 X·바깥 클릭·Escape로 닫거나 계속 편집하기를 선택하면 수정 내용이 유지된다.

빌드·타입·포맷 검사와 관련 Chromium 화면 시험 6개를 통과했다. 320px, 짧은 가로 화면, 데스크톱에서 버튼 정렬·내용 유지·초점 복귀와 기존 문구 드래그·저장·설치 안내를 확인했다. Hosting에 배포한 파일 12개의 해시가 로컬 빌드와 일치했다. 공개 주소에서도 나가기 창 닫기, 미저장 문구 확인·계속 편집·저장, 대화·재입장·방 소유권과 삭제를 확인하고 이 실행의 임시 계정 4개 및 역할 정보와 시험 방을 정리했다. Firebase 인증 설정·보안 규칙·요금제는 이번 배포에서 변경하지 않았다.

## 관리자 승인 적용 — 2026-10-09

사용자가 지정한 기존 이메일 계정을 관리자로 연결했다. 다른 기존 계정도 한 번 승인받도록 하는 선택을 적용했다. 기존 Firebase Authentication 계정·역할 정보·방은 삭제하지 않았으며, 지정 관리자 외에는 승인 기록이 없으면 승인 대기 상태로 취급한다. 관리자 이메일은 공개 소스에 넣지 않고 Firebase UID로 권한을 연결한다.

- 회원가입에서 신청한 역할과 인증 계정의 이메일을 저장한다. 이전 역할 정보에 이메일이 없으면 해당 사용자 로그인 시 자기 인증 이메일만 보충한다. 자기 역할·가입 시각을 바꾸거나 다른 이메일로 신청하는 쓰기는 거절한다.
- `administrators/{uid}`의 권한은 신뢰된 Firebase 관리 작업으로만 지정한다. 일반 방송실 역할과 구분한다. `access/{uid}`의 승인·거절 상태는 관리자만 변경할 수 있고 자기 자신이나 다른 관리자 권한을 바꿀 수 없다. 관리자 최초 지정은 해당 관리자에 한해 승인 상태도 함께 설정한다.
- 승인 대기·거절 계정은 방 목록, 입장, 기존 방 읽기, 메시지, 방 생성·삭제가 모두 서버에서 차단된다. 기존 익명 연결도 방을 읽을 수 없으며 자기 연결 정리만 허용한다. 승인 취소 시 기존 방 구독·화면·재입장 힌트를 지우고 자기 접속을 해제한다. 연결 정리가 확인되기 전에는 서버의 종료 예약을 유지한다.
- 홈의 ‘가입 승인 관리’는 지정 관리자에게만 표시한다. 상태별 목록에서 이메일과 역할을 보고 승인·거절·승인 취소를 확인창으로 처리한다. 거절한 신청은 나중에 승인할 수 있다. 승인 결과는 신청자 화면에 실시간 반영한다. 승인 대기 계정도 로그아웃과 비밀번호 재설정은 가능하다.
- Cloud Functions, 유료 이메일 알림, 초대코드는 추가하지 않았다. Firebase Authentication 계정은 가입 시 생성되며, 승인은 서비스 이용 권한을 제어한다. 에뮬레이터 최초 관리자는 `npm run local:admin -- 테스트이메일`로 지정할 수 있고 이 도구는 localhost의 demo 프로젝트만 접근한다.

빌드·타입·포맷 검사, 단위 시험 5개, 현재 서버 규칙 시험 19개와 이전 자동 삭제 후보 실험 3개, Chromium 화면 시험 28개를 통과했다. 권한 위조·자기 승인·타인 신청 조회 차단, 기존 회원 승인 대기, 관리자 승인·거절·실패 후 재시도·승인 취소와 접속 정리, 기존 대화·로그인·문구 편집 동작을 검증했다. 로컬 관리자 지정 도구도 임시 계정으로 확인하고 시험 자료를 정리했다.

Hosting과 데이터베이스 규칙을 배포했다. 실제 사이트 파일 12개가 운영 빌드와 일치하며, 임시 관리자 화면에서 다른 시험 계정을 거절·승인하고 승인 전 서버 접근 차단 및 승인 후 대화·재입장·방 소유권을 확인했다. 해당 실행의 임시 계정 4개, 역할·승인 기록·시험용 관리자 권한과 방을 정리하고 지정 관리자만 남아 있음을 확인했다. 결제 계정 미연결(`billingEnabled: false`)을 다시 확인했다. 실제 iPhone·Mac Safari 검증은 남아 있다.

### 관리자 첫 화면 수정 — 2026-10-09

방송실·예배인도자 역할 정보가 없는 관리자에게도 일반 계정의 역할 설정을 먼저 표시하던 화면 분기를 수정했다. 관리자는 로그인·새로고침 후 곧바로 가입 승인 관리 화면으로 들어가며, 계정 표시도 ‘관리자’로 나온다. 관리자가 명시적으로 ‘대화 참여’를 누를 때만 대화용 역할을 한 번 선택한다. 역할 선택을 하지 않고 승인 관리로 돌아갈 수 있으며, 승인 관리 자체는 역할 정보 없이 동작한다. 서버의 승인 권한과 대화방 소유권 규칙은 그대로 유지했다.

빌드·타입·수정 파일 포맷 검사와 Chromium 승인 관련 시험 3개를 통과했다. 역할이 없는 관리자의 로그인·새로고침·가입 승인, 선택적인 대화 역할 설정, 기존 역할 계정의 승인 대기, 승인 취소에 따른 대화 접근 중단을 확인했다. Hosting 배포 후 실제 사이트에서도 별도 임시 관리자에게 역할 정보를 만들지 않은 상태로 같은 승인 흐름을 검증했다. 임시 계정 2개와 해당 계정의 역할·승인·관리자 기록을 모두 제거했고, 배포 파일 12개가 로컬 빌드와 일치함을 확인했다.

### 관리자 기본 홈과 입장별 역할 선택 — 2026-10-09

사용자의 후속 요청으로 위 관리자 첫 화면 정책을 변경했다. 관리자는 로그인하면 일반 홈의 방 목록을 보며, 가입 승인 관리는 헤더 버튼으로 연다. 관리자에게 계정 역할 설정을 요구하지 않는다. 새 방은 방송실로 만들고, 기존 방에는 비밀번호 입력과 함께 그 입장에서 사용할 방송실·예배인도자 역할을 선택한다. 방을 나간 뒤 재입장할 때 다른 역할을 선택할 수 있다. 이 선택은 방의 회원 정보에만 반영하며, 이전에 저장된 계정 역할이 있어도 관리자의 참여 역할을 제한하지 않는다.

클라이언트의 방 목록·생성·입장·복원·전송 검사와 서버의 역할 검사 7곳에 관리자 예외를 적용했다. 승인 상태, 방 비밀번호, 입장 역할과 메시지 역할의 일치, 역할별 한 명, 접속 중 역할 변경 금지, 방 생성자의 종료 권한은 유지한다. 일반 계정의 역할 고정과 관리자 권한 위조 차단도 유지한다. 관리자 지정이 해제되면 일반 계정의 역할 제한으로 돌아가며 기존 접속의 정리는 허용한다.

빌드·타입·전체 포맷 검사, Chromium 화면 시험 29개, 서버 규칙 시험 25개와 이전 자동 삭제 실험 3개를 통과했다. 처음 서버 시험은 로컬 에뮬레이터가 꺼져 있어 실행되지 않았으며, 에뮬레이터를 시작한 뒤 정상 통과했다. Hosting과 데이터베이스 규칙을 배포하고 파일 12개의 일치를 확인했다. 실서비스의 첫 메시지 수 검사는 기본 5초 대기에서 시간초과되어 대기를 20초로 늘려 재검증했다. 이후 기본 홈 진입, 승인 관리, 관리자 방송실 생성·예배인도자 재입장·역할별 전송·새로고침 복원·방 종료를 확인했다. 두 번의 실서비스 검증에서 만든 임시 계정 총 4개와 각각의 방·역할·승인·관리자 기록을 정리했다. 실제 사용자의 계정이나 저장된 역할은 변경하지 않았다.


## 보안·무료 운영 보완 — 2026-10-09

Chromium 화면 검사 37개를 통과했다. 이메일 인증과 별도 승인, 이전 대화 페이지, 참여 중 방의 삭제 거절과 빈 방 삭제, 화면 꺼짐 방지 해제, 기존 로그인·양방향 대화·문구·모바일 크기의 UI를 포함한다. 실제 iPhone·Mac Safari나 이메일 수신 성공을 의미하지 않는다. 현재 서버 규칙 33개와 이전 자동 삭제 방식 실험 3개, 단위 시험 6개, 포맷 검사와 운영 빌드도 통과했다.


Firebase Hosting과 데이터베이스 규칙에 반영했고 배포된 파일 12개의 해시가 운영 빌드와 일치했다. 실제 HTTPS 주소에서 이메일 인증 상태에 따른 접근 제한, WebSocket이 없는 환경의 long polling, 양방향 대화, 퇴장 후 직접 대화 읽기 차단, 재입장 기록 복원, 방·목록·소유 슬롯 삭제를 확인했다. 보안 헤더와 Firebase 이메일 처리 예약 경로도 확인했으며 브라우저 오류·CSP 위반은 없었다. 첫 운영 시험 두 번은 스크립트에 퇴장 확인 버튼 클릭이 누락돼 중단됐고, 이를 보완한 세 번째 시험은 통과했다. 각 실행의 임시 계정 3개씩 총 9개와 그 설정·방만 정리했다. 실제 사용자 계정이나 승인은 바꾸지 않았다.

운영 변경 전에 설정 백업을 로컬 비공개 폴더에 만들었고, 방이 0개라 기존 대화 이전은 필요하지 않았다. 결제 계정은 연결되지 않은 상태다. 공개 저장소 푸시 및 GitHub 배포용 계정·권한 연결은 별도 확인이 남아 있다.
